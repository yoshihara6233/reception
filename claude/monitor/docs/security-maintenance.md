# 依存の更新と重い処理の決まり（G・VMS-Cloud）

作成: 2026-10-30 / 対象: `claude/monitor`（Next.js・Vercel）・`claude/edge-agent`（Bun）・`packages/shared`・Supabase
自主診断（ASVS 5.0 L2）の **15.1.1**（第三者の部品の是正の期限と、ふだんの更新の周期）と **15.1.3**（時間や資源を多く使う処理と、その守り方）の文書です。
検査の仕組みの全体は `docs/security-assessment.md`（リポジトリの直下）にあります。ここでは「いつまでに・どの周期で・どう守るか」を決めます。

## 1. 依存の脆弱性の是正の期限（15.1.1）

### 1.1 見つける仕組み

| 何を | 仕組み | いつ |
|---|---|---|
| npm の依存（`bun.lock`） | `security.yml` の `deps-audit`（`bun audit` → `.github/scripts/audit-gate.mjs`） | すべての PR・`monitor-prod` への push・**毎週月曜 03:00（日本時間）** |
| GitHub Actions | `.github/dependabot.yml`（SHA 固定の追従） | 毎週 |
| コード（SAST・秘密の混入） | `security.yml` の `semgrep` | すべての PR・毎週月曜 |
| エッジの OS の部品（cloudflared・ffmpeg など） | 提供元の告知と、月次の更新の点検（§2） | 月 1 回 |

audit-gate は high / critical を見つけると CI を落とします。受け入れる（すぐ直さない）ときは `.github/security-exceptions.json` に理由と期限（`until`）を書きます。期限を過ぎた受け入れ・直ったのに残っている受け入れでも CI が落ちます。

### 1.2 重さ別の期限

重さは勧告の重さ（GitHub Advisory・CVSS）を使います。「使っている」は、脆弱な関数や経路を本番のコードが通ることを指します（開発の道具だけ・使わない機能だけなら「使っていない」）。

| 重さ | 使っている | 使っていない（到達しない） |
|---|---|---|
| critical | **72 時間以内**に本番へ（夜間・休日も対応） | 7 日以内 |
| high | **7 日以内**に本番へ | 30 日以内 |
| moderate | 30 日以内 | 次の月次の更新（§2） |
| low | 次の月次の更新 | 次の四半期の更新 |

- 期限は「勧告が出た日」ではなく「こちらが知った日」（audit-gate が落ちた日・告知を受けた日）から数えます。
- 期限までに直せない（上流に直しが無いなど）ときは、`security-exceptions.json` に受け入れを書き、`until` を上の期限より先にしません。期限が来たら見直して書き直します（黙って延ばさない）。代わりの守り（設定で機能を止める・経路を塞ぐ）があれば、理由の欄に書きます。
- 本番のクラウドで直ったことは、配備のあとに確かめます（版の表示・応答のヘッダーなど）。エッジは OTA の配布が全拠点に届いたことまでを完了とします。
- 秘密の鍵が漏れた疑い（依存の乗っ取りなど）は critical と同じ扱いにし、鍵の作り直しを含めます。

## 2. ふだんの更新の周期（15.1.1）

脆弱性が無くても、古い版のまま溜めないための周期です。

| 対象 | 周期 | 中身 |
|---|---|---|
| npm の依存（patch・minor） | **月 1 回**（月の第 1 週） | `bun outdated` を見て更新 → CI（vitest・tsc・eslint・authz・E2E）→ PR |
| Next.js・React・Supabase のクライアント | 月 1 回（上と同じ PR か別の PR） | 提供元の更新の告知を読み、破壊的な変更が無いことを確かめる |
| npm の依存（major） | **四半期に 1 回**見直す | 移行の手間と、古い版の保守が切れる時期で決める。保守が切れる版は使い続けない |
| GitHub Actions | 毎週（Dependabot の PR） | SHA 固定のまま上げる |
| 実行環境（Bun・Node.js・CI の版） | 四半期に 1 回 | `package.json` の `packageManager`・CI の `bun-version` をそろえて上げる |
| エッジの部品（cloudflared・OS の更新） | 月 1 回の点検 | 告知を見て、必要ならエッジの更新（OTA・現地）を計画する |
| Supabase・Vercel（基盤） | 提供元が管理 | 告知（メール・ダッシュボード）を見て、こちらの設定の変更が要るものだけ対応する |

更新の PR には、何を上げたか・告知で読んだ破壊的な変更の有無を書きます。

## 3. 時間や資源を多く使う処理（15.1.3）

### 3.1 前提（全体にかかる守り）

- **関数の時間の上限**: Vercel の関数は `maxDuration` で止まります。指定の無いものはプロジェクトの既定の上限です。上限を超えた要求は 504 で終わり、続きの処理は残りません（途中までの書き込みに注意）。
- **DB の問い合わせの時間の上限**: Supabase は `authenticated`・`anon` の接続に `statement_timeout` を掛けています（既定）。利用者の接続からの長い問い合わせはここで止まります。サービスの接続（cron・サーバの処理）には掛かりません。
- **要求の大きさ**: Vercel の関数が受ける本文は 4.5 MB までです（CSV の取り込みの大きさもここで頭打ち）。
- **ログインまわりの回数の制限**: ログイン・パスワードの再設定・多要素の番号・エッジのエンロールは、利用者ごと・IP ごとの回数で縛っています（`lib/rate-limit.ts`）。
- **重い処理の回数の上限**（2026-10-30）: 下の表の重い処理は、利用者（キオスクは店舗）ごとの回数で縛ります（`lib/limits/heavy.ts` の `HEAVY_LIMITS`・判定は DB の `rate_limit_hit`）。「60 秒に N 回」の短い窓を同時数の代わりにし（どの処理も普通は 60 秒より短く終わるので、同時に走るのも実質 N 本まで）、1 時間の窓で総量を縛ります。超えたら 429 と日本語の文（`message`）を返し、`[security] {"kind":"rate_limited"}` を記録します。DB に届かないときは通します（フェイルオープン・認可の境界ではない）。
- **外への fetch の時間切れ**（2026-10-30）: サーバ側の `fetch` はすべて `signal`（`AbortSignal.timeout`）を持ちます。本文を利用者へ流す中継（録画の HLS の断片）は、見出しが届くまでだけを数えます（`lib/net/fetch-timeout.ts`）。`src/test/heavy-limits.test.ts` が signal の無い fetch を見つけると CI を落とします。

### 3.2 一覧と対策

| 処理 | 受け口 | 重さの元 | 今の守り | 残 |
|---|---|---|---|---|
| ライブ・録画の視聴（HLS・画像の中継） | `/api/live-proxy`・`/api/vod-hls`・`/api/edges/[id]/grid` | 帯域・拠点への要求（16 分割は 1〜2 秒ごとの取得） | テナントごとの**同時視聴数の上限**（`session_limits`・DB の関数で数えて断る）と **1 回の連続視聴時間**（既定 120 分・テナントごと）。中継の Cookie は 10 分で切れ、視聴中だけ延びる。middleware の判定はトークンごとに 30 秒覚えて往復を減らす | — |
| BCP の画像の ZIP | `GET /api/bcp/[id]/snapshots.zip` | 1 件の BCP の画像（拠点のカメラ数 × 取る時点の数）を全部メモリに読み、まとめて圧縮して返す | ログインと RLS（見える拠点だけ）。1 件の BCP に限られる。**流しながら作る**（1 枚ずつ取り、先読みは 4 枚・`lib/bcp/zip-stream.ts`）。画像 2,000 枚・合計 1 GiB まで。`maxDuration` 300 秒。**回数**: 利用者 60 秒 2 回・1 時間 20 回、アプリ全体で 60 秒 20 本 | — |
| BCP の報告書（PDF） | `POST /api/bcp-webhook`（拠点のアップロードが済んだあと・Bearer の秘密）・`POST /api/bcp/[id]/generate-report`（画面から作り直し） | PDF の組み立て（`@react-pdf/renderer`）と画像の署名 URL | 通常は**非同期**（拠点の送信が終わってから webhook で作り、Storage に置いてメールで知らせる）。利用者は出来上がった PDF を取りに行くだけ。画面からの作り直しは同期で、**回数**: 利用者 60 秒 3 回・1 時間 30 回、アプリ全体で 60 秒 20 本 | — |
| 月次レポート（PDF） | `/api/cron/monthly-report`（毎日 06:00・`maxDuration` 300 秒）・`POST /api/admin/reports/monthly`（管理者の手動確定） | テナントごとの集計と PDF | cron で**事前に作って保存**し、利用者は保存したものを読む。手動の確定は管理者だけ。**回数**: 利用者 60 秒 3 回・1 時間 30 回（過去の月をまとめて確定できる数）、同じテナント 60 秒 3 回 | 手動の確定は同期で、テナントの規模が大きいと上限に近づく |
| 自主巡回の報告（PDF）・手動巡回 | `/api/cron/security-report`（300 秒）・`/api/cron/security-patrol`（10 分ごと・120 秒）・画面の「巡回」 | 拠点ごとの点検と PDF | cron で非同期。手動の巡回は選んだ拠点ごと | 手動で多くの拠点を一度に選ぶと時間が延びる |
| CSV の取り込み（拠点・カメラ） | `POST /api/admin/import/stores`・`/cameras` | 行ごとの検査と書き込み | 管理者だけ。拠点数の上限（テナントの契約）を行ごとに確かめる。本文は 4.5 MB まで。**行数**: 拠点 1,000 行（1 行ずつ書くので 300 秒に収まる数）・カメラ 5,000 行（1 回の upsert）。超えたら 413 で分けてもらう（`lib/admin/csv.ts` の `CSV_MAX_ROWS`）。**回数**: 利用者 60 秒 3 回・1 時間 30 回 | — |
| 定期の処理（cron） | `vercel.json` の 13 本 | 全テナント・全拠点を回る | `CRON_SECRET` でだけ動く。重いものは `maxDuration` を明示（usage-rollup・monthly-report・security-report・baggage-daily は 300 秒、security-patrol 120 秒、edge-health 60 秒）。間隔の短いもの（edge-health・alarm-dispatch-retry 2 分、sfu-reaper・video-sessions 5 分）は、前の回が終わる前に次が来ても壊れないよう、行ごとの状態で進める | 拠点が増えると 1 回で回りきれなくなる。→ 拠点数の増加に合わせて、テナントごとに分ける・続きを次の回に回す |

| 更新の配布物のアップロード | `POST /api/admin/nvmsd-releases` | 大きいファイルの検査 | 運営（super_admin）だけ。`maxDuration` 60 秒 | — |

| VOD の依頼 | `POST /api/vod` | 拠点の録画の切り出しと送り出し | ログインと RLS。同じ範囲は使い回す。**回数**（新しく作るときだけ）: 利用者 60 秒 10 回・1 時間 120 回。拠点への指示は 10 秒で時間切れ | — |
| 住所の座標 | `GET /api/geocode`・`GET /api/admin/geocode` | 外部（zipcloud・Nominatim） | ログイン。**回数**: 利用者 60 秒 10 回・1 時間 100 回。Nominatim は**アプリ全体で 1 秒 1 回**（OSM の約款。超えるとこちらの IP が遮断される）。応答待ちは 8 秒まで | — |
| 秘密の包み直し | `POST /api/admin/secrets/rewrap` | 全カメラの資格情報の再暗号化 | 運営だけ。`maxDuration` 60 秒 | 件数が増えたら分割 |

### 3.3 応答が利用者の待ち時間より長くならないようにする

- **重いものは先に作っておく**: 月次レポート・巡回の報告・BCP の報告書は、cron か webhook で作って Storage に置き、利用者は出来上がったものを読みます。
- **画面からの同期の重い処理**（報告書の作り直し・月次の手動確定・CSV の取り込み）は、関数の上限より十分に短く終わる規模を前提にし、回数と行数で縛っています。BCP の ZIP は流しながら作るので、利用者は最初の数枚が届いた時点からダウンロードが進みます。月次の手動確定が前提を超える規模の顧客を入れる前に、非同期にして出来上がりを知らせる形へ移します。
- **新しく重い処理を足すとき**は、この表に行を足し、`maxDuration`・誰が呼べるか・回数や同時数の上限（`HEAVY_LIMITS` に足す）・非同期にするかを決めてから作ります。受け口は `src/test/heavy-limits.test.ts` の表にも足します。
