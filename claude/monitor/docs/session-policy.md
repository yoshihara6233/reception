# セッションの期限の決まり（G・VMS-Cloud）

作成: 2026-10-30 / 対象: `claude/monitor`（画面と API）・Supabase Auth
自主診断（ASVS 5.0 L2）の **7.1.1**（無操作の期限と最長の期限を文書にし、NIST SP 800-63B の再認証の要件から外れるところは理由を書く）の文書です。

---

## 1. 決め

| 期限 | 値 | どこで効くか |
|---|---|---|
| **無操作の期限**（inactivity timeout） | **24 時間** | Supabase Auth の Sessions → Inactivity timeout。セッションのトークンが 24 時間更新されなければ、そのセッションは使えなくなり、ログインし直し |
| **最長の期限**（time-box） | **7 日（168 時間）** | Supabase Auth の Sessions → Time-box user sessions。ログインから 7 日で、使っていてもログインし直し |
| アクセストークンの有効時間 | 1 時間 | Supabase Auth の JWT expiry（`jwt_expiry = 3600`）。画面は使っている間に自動で更新する |
| リフレッシュトークン | 使うたびに作り直す（再利用の猶予 10 秒） | `enable_refresh_token_rotation = true` |
| 映像の 1 回の連続視聴 | 上限なし（2026-10-31 に廃止・発注者の判断。同時視聴の上限で帯域を抑える） | — |
| 手荷物検査のキオスク（PIN） | 12 時間 | キオスクのセッションの Cookie（`lib/baggage/kiosk-pin.ts`）。利用者のログインとは別 |
| 中継の Cookie（ライブ） | 10 分（視聴中は延びる） | `lib/live-proxy-session.ts` |

「無操作」は、Supabase Auth がトークンを更新したかどうかで決まります（画面のマウスやキーの操作ではありません）。開いている画面は 1 時間ごとに自動で更新するので、**本部の監視の画面を開いたままにしても 24 時間では切れません**。切れるのは、端末を閉じた・ブラウザを終えた状態が 24 時間続いたときです。最長の 7 日は、開いたままでも効きます。

### 1.1 期限のほかにセッションを終える手段

- ログアウト: その人のすべてのセッションを失効させ、端末の控え（Service Worker の Cache Storage・HTTP の控え）を消す（ASVS 14.3.1）
- 管理者の「セッションを切る」「利用を止める」（利用者の編集の画面・ASVS 7.4.2・7.4.5）
- テナントの停止（ログイン・拠点の SSO・拠点からの受信が止まる）
- 切ったセッションのアクセストークンは、画面・API（`getUser`）でも DB（RESTRICTIVE のポリシー `user_active_only`）でも、その時点から使えない（1 時間の有効時間を待たない）

## 2. 設定の場所

- **本番**: Supabase のダッシュボード → Authentication → Sessions の「Time-box user sessions」に `168h`（7 日）、「Inactivity timeout」に `24h`。どちらも有料のプランの機能です。設定を変えたら、この文書と `supabase/config.toml` を同じ値にそろえます。
- **手元・CI**: `supabase/config.toml` の `[auth.sessions]`（`timebox = "168h"`・`inactivity_timeout = "24h"`）。

## 3. NIST SP 800-63B（第 4 版）との比べ

NIST は、認証の強さ（AAL）ごとに再認証の間隔を示しています。G・VMS-Cloud のログインはパスワード（AAL1 相当）で、多要素（認証アプリの番号）を登録した人は AAL2 相当です。

| | NIST の目安 | この決め | 合っているか |
|---|---|---|---|
| AAL1 の最長 | 30 日を超えない | 7 日 | 合う（短い） |
| AAL1 の無操作 | 定めなし | 24 時間 | 合う |
| AAL2 の最長 | 24 時間を超えない | 7 日 | **外れる** |
| AAL2 の無操作 | 1 時間を超えない | 24 時間 | **外れる** |

### 3.1 外れるところの理由と、代わりの守り

**理由**
- 本部の監視の画面（壁のモニタ・常時表示の PC）は、開いたまま何日も映像と発報を出し続けるのが本来の使い方です。24 時間ごとの再ログインは、夜間・休日に監視の画面が止まり、発報を見落とす危険を生みます。
- スマートフォン（PWA）は、発報の通知から開いてすぐ映像を見る使い方です。毎日のログインし直しは、緊急時の初動を遅らせます。
- Supabase Auth の期限はプロジェクトで 1 つで、AAL ごとに分けられません。AAL2 に合わせると、AAL1 の人まで 24 時間・1 時間になります。

**代わりの守り**
- アクセストークンは 1 時間で、セッションを切るとその時点から画面・API・DB のどれにも使えない（管理者の「セッションを切る」「利用を止める」・ログアウト）
- 多要素を登録した人は、ログインのたびに番号を確かめる（7 日に 1 回は必ず）
- 映像の同時視聴数はテナントごとに上限がある（連続視聴の時間の上限は 2026-10-31 に廃止）
- ログアウトで端末の控えを消し、認証済みの画面は端末に控えない（共用の端末に前の人の画面が残らない）
- 利用者の権限は拠点の割り当てで絞られ、DB の RLS が最後に止める

## 4. 仕様書の「アイドル 5 分で自動ログアウト」について

仕様書（`docs/recorder-monitoring-spec.html` の F-10 と、非機能のセッションの行）は「同一ユーザのアイドル自動切断（5 分）」「アイドル 5 分で自動ログアウト」と書いています。**実装はこれをしていません**（画面の操作の有無でログアウトする仕組みは無く、2026-10-30 までは Supabase Auth の期限も設定していなかった＝ログアウトしない限りセッションは続いた）。

この文書の決め（無操作 24 時間・最長 7 日）を正とし、仕様書の 5 分は採りません。理由は §3.1 と同じです（監視の画面は操作が無いのが普通で、5 分で切ると監視そのものが成り立たない）。仕様書の同じ行に含まれる「同時セッション上限・最大連続視聴時間」は、視聴の同時数の上限と 1 回 120 分の上限として実装しています。「管理者による強制セッション無効化」は、利用者の編集の画面の「セッションを切る」「利用を止める」で実装しました。

**残**: 仕様書の F-10 と非機能の行を、この文書を指す書き方に直す。

## 5. 見直し

認証の方式（多要素の必須化・SSO の一本化など）を変えるとき、または四半期の態勢監査（`docs/security-assessment.md`）のときに見直します。多要素を全員に必須にした場合は、AAL2 の目安に近づける（最長 24 時間・無操作 1 時間を、監視の画面の運用と合わせて検討する）ことを先に考えます。
