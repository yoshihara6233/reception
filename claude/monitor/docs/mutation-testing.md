# 変異テスト（mutation testing）

実装をわざと少しずつ壊し（`>` を `>=` に、`&&` を `||` に、条件を `true` に…）、
**テストが気づくか**を機械的に測ります。カバレッジが「その行を実行したか」しか
見ないのに対し、こちらは「壊したら落ちるか」を見ます。

## なぜ入れたか

2026-08-09、webhook のフェイルクローズを**正規表現でソースの形から**検査して
いましたが、壊した実装がその検査を素通りしました。

```ts
// 検査は「!secret のとき 500 を返す」形を探していた
if (!expectedSecret) { /* 何もしない */ } else { … }   // ← 素通りした
```

検査そのものが嘘をついていた、という状態です。その日は 11 通りの変異を手作業で
かけて確認しましたが、手作業は続きません。機械にやらせます。

## 動かし方

```bash
bun run test:mutation                                   # 全対象（約 45 秒）
bunx stryker run --mutate 'src/lib/bcp/intensity.ts'    # 1 ファイルだけ
```

結果は `reports/mutation/index.html`。生き残った変異が行単位で見られます。

CI は**週次**（毎週月曜 04:00 JST）と手動実行。PR ごとには回しません — 指摘は
「テストを厚くする」という別作業になりがちで、PR を止める性質のものではないためです。
ただし `stryker.config.mjs` 自体を変えた PR では走ります。

## 対象の選び方

全部にかけると遅すぎて誰も回さなくなります。**間違えると権限・署名・可用性が
壊れるもの**だけを `stryker.config.mjs` の `mutate` に並べています。

| 分類 | 対象 |
|---|---|
| 誰が何を見られるか | `lib/tenant/`・`lib/admin/user-scope`・`super-admin-floor`・`lib/edge/`・`middleware.ts` |
| 署名・トークン | `live-sign`・`edge-images-sign`・`token-cache`・`kiosk-pin`・`rate-limit` |
| 発令・監視の判定 | `bcp/intensity`・`ops/partition-health`・`ops/tunnel-health`・`jalert-poller/match` |

UI や整形処理は対象外です。そこは変異が生き残っても困りません。

**足すときは「壊れたら何が起きるか」を言えること。** 言えないものは対象にしません。

## 導入時に見つかったもの（2026-08-09）

| 場所 | 何が起きていたか |
|---|---|
| `bcp/intensity.ts` | `intensityRank` に**テストが 1 件も無かった**。順序表の要素を 1 つ壊しても（`'6+'` → `''`）誰も気づかない。**BCP の発動しきい値はこの順序に全面的に依存する** |
| `jalert-poller/match.ts` | `isJisPref` の `n >= 1 && n <= 47` を `>` や `<` に変えても落ちなかった。**38 店舗への誤発報を生んだ領域そのもの**の境界が未検証 |
| `ops/partition-health.ts` | 分岐が 3 本あるうち **3 本目に到達する値が存在しなかった**（`warn` を一度も出せない）。定数のコメントに書いた意図と実装がずれていた。当日書いたばかりのコード |

いずれも「テストはあるのに守っていない」形で、カバレッジでは見えません。

| 対象 | 導入前 | 是正後 |
|---|---|---|
| `bcp/intensity.ts` | 38.89% | **86.11%** |
| `ops/partition-health.ts` | 63.27% | **89.47%** |
| `jalert-poller/match.ts` | 68.68% | **74.18%** |
| 全体 | 64.38% | **69.98%** |

## 続けてエッジ側 3 モジュール（同日）

上の 3 件と**まったく同じ形**でした——純粋な補助関数にはテストがあり、
**実際に I/O を伴うセキュリティ本体だけが未検証**。

| モジュール | 未検証だった関数 | 導入前 | 是正後 |
|---|---|---|---|
| `edge/auth-provision.ts` | `ensureEdgeAuthPassword`（エッジ認証ユーザの払い出し） | 11.43% | **85.71%** |
| `edge/view-access.ts` | `requireEdgeViewAccess`（ライブ画像の認可ゲート） | 33.33% | **82.46%** |
| `storage/edge-images-sign.ts` | `workerImageExists`（R2 の存在確認とメモ化） | 42.00% | **76.00%** |

全体 69.98% → **80.17%**。「no coverage」は **139 → 22**。

固定した主な契約:

- 鍵（`SECRETS_ENC_KEY`）が無ければ **Auth を一切触らない**（平文パスワードを作らない）
- email 衝突時は既存ユーザを引き当てて更新に回す（同時実行でエッジを丸腰にしない）
- 保存されるのは**暗号化されたパスワード**（平文を書かない）
- 認可ゲートは未ログイン 401 / 可視外 403 を取り違えない
- **判定不能（DB 障害）の 403 はキャッシュに焼き付けない**（瞬断で締め出さない）
- キャッシュはトークン×エッジ単位（1 台見えたら全台見える、にしない）
- R2 の存在確認は**肯定 60 秒・否定 3 秒**（この非対称を消すとライブ開始が不安定になる）

## しきい値

`thresholds.break = 75`。実測 80.17% の少し下に置いています（導入時は 65 → 実測の向上に合わせて引き上げ）。

`break` の役目は**回帰を捕まえること**で、目標を掲げることではありません。実測値
ちょうどに置くと変異の揺らぎで落ちます。上げるのは歓迎、**下げるときは
`stryker.config.mjs` に理由を書いてください**。

## 次に手を入れるなら

低い順です。数字を上げること自体が目的ではなく、**「no coverage」が多い＝
そのモジュールの分岐にテストが一度も触れていない**という事実が問題です。

| モジュール | スコア | 状況 |
|---|---|---|
| `admin/super-admin-floor.ts` | 70% | 下限ガード（最後の 1 人を消させない） |
| `tenant/features.ts` | 70% | オプション機能フラグの出し分け |
| `admin/user-scope.ts` | 73% | 店舗 ID のテナント越境チェック |
| `jalert-poller/match.ts` | 74% | 生き残り 38（no coverage は 9） |
| `storage/edge-images-sign.ts` | 76% | 署名生成側に生き残りが残る |

**性質が変わった点に注意。** 導入時の課題は「no coverage＝分岐にテストが
一度も触れていない」でしたが、それは 139 → 22 まで減りました。残りはほぼ
**生き残り変異**（テストは通っているが壊しても気づけない）で、1 件ずつ
「これは実害があるか」を判断する作業になります。**数字を追う段階は終わり**、
ここからは選ぶ段階です。

## 注意

- **数字を上げるために対象を外さないこと。** 未検証のセキュリティコードを除外すれば
  スコアは上がりますが、それは事実を隠しているだけです。`tenant/session.ts` を
  外しているのは「分岐が実質無く、変異させてもモックを突くテストしか生まれない」
  という別の理由で、設定にその旨を書いてあります。
- 生き残った変異のすべてを潰す必要はありません。ログ文言や定数表記のように
  「壊れても実害が無い」ものは残して構いません。**判断が要ります。**
