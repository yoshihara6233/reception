## 1. 認証の経路（6.1.3）

G・VMS-Cloud に入る経路は次のとおりです。**利用者（人）の経路は、どれもメールとパスワード（＋登録した人は認証アプリの番号）の 1 つの強さにそろえます。** パスワードを使わずに利用者のセッションを作る抜け道（マジックリンク・メールの番号だけのログイン・匿名のログイン・外部の IdP）は置きません。

### 1.1 人の経路

| 経路 | 入口 | 強さ | 主な統制 |
|---|---|---|---|
| ログイン | `POST /api/auth/login`（サーバから Supabase Auth） | パスワード（AAL1）。多要素を登録した人は認証アプリの番号まで（AAL2） | 回数の制限（§2）・誤りの文は 1 種類・同じサイトの画面からの JSON だけ・セッションは HttpOnly の Cookie |
| 多要素の番号 | `POST /api/auth/mfa`（ログインの途中）・`/login/mfa` | TOTP（6 桁・30 秒） | 利用者ごと 10 回 / 15 分。番号を済ませるまで middleware が画面と API を通さない |
| パスワードの再設定 | `POST /api/auth/reset-link` → メールの 6 桁の番号 → `POST /api/auth/recovery/verify` | メールの受け取り＋番号 | メール 3 回 / 時・IP 10 回 / 時（送る側）、メール 5 回 / 15 分・IP 20 回 / 時（番号）。番号は画面に出さない。再設定の画面は、番号で入ってから 15 分のセッションでだけ使える（`lib/auth/recovery-session.ts`） |
| 仮のパスワード | 管理者が利用者を作る・再発行する（管理の画面） | 管理者が決めたパスワード | 72 時間で使えなくなる。入ったら本人のパスワードに変えるまで他の画面へ進めない（`lib/auth/initial-password.ts`） |
| 拠点（G・VMS）への SSO | 拠点の「組織アカウントでサインイン」→ Supabase の OAuth 2.1 Server → 同意の画面 `/oauth/consent` | **クラウドのログインをそのまま使う**（多要素を登録した人は番号を済ませてから同意の画面へ） | 承認は「サインイン」を押したときだけ・その拠点に入れる人だけ・許可の期限（§5）。拠点へ出したトークンはクラウドの画面・API・DB で使えない（`lib/auth/foreign-client.ts`・RLS の `first_party_only`） |
| 手荷物検査のキオスク | `POST /api/baggage/kiosk/pin-login`（店舗ごとの 6 桁の PIN） | 店舗の共用の PIN（利用者のログインではない） | 店舗ごと 5 回の失敗で 15 分ロック。発行するのはキオスクの受け口だけに使える 12 時間の署名の Cookie。履歴や管理の画面には入れない |

### 1.2 機械の経路

| 経路 | 入口 | 強さ | 主な統制 |
|---|---|---|---|
| エッジ（edge-agent・G・VMS の nvmsd） | `/api/edge/*` の `Authorization: Bearer <device token>` | 機器ごとのランダムなトークン | DB には要約（ハッシュ）だけを置く。届く範囲はその機器の店舗だけ。設置コードによる登録（`/api/edge/enroll`）は IP ごとの回数の制限 |
| 定期の処理（Vercel Cron） | `/api/cron/*` | 共有の秘密（`CRON_SECRET`） | 未設定なら 503（だれも通さない） |
| 外からの通知（Webhook） | `/api/bcp-webhook`・`/api/webhooks/onvif/[storeId]` | 共有の秘密 | 未設定なら断る（フェイルクローズ・試験で固定） |
| Supabase の REST（PostgREST）を直接 | `https://<project>.supabase.co/rest/v1/*` | 利用者のアクセストークン | すべての表に RLS。拠点向けのトークン・切ったセッション・止めた利用者のトークンは RESTRICTIVE のポリシーで断る |
| 運営（Supabase のダッシュボード・service_role の鍵） | Supabase のダッシュボード・Vercel の環境変数 | 各サービスのアカウント（多要素） | 鍵の作り直しの手順は `docs/dr-runbook.md` |

### 1.3 置いていない経路

- **新規登録（サインアップ）の画面は無い。** 利用者は管理者が作る。Supabase の「Allow new users to sign up」は本番で切っておく（§6 の確認事項）。切っていなくても、作られたアカウントは `admin_users` に行が無いので、どの画面・データにも届かない。
- マジックリンク・メールの番号だけのログイン・SMS・匿名のログイン・外部の IdP（Google など）は使わない。

## 2. 回数の制限と、嫌がらせのロックの防ぎ方（6.1.1）

### 2.1 回数の制限

| 何を | 単位 | 上限 | どこで |
|---|---|---|---|
| ログイン | メールアドレス | 10 回 / 15 分 | アプリ（`/api/auth/login`・DB の `rate_limit_hit`） |
| ログイン | 送り元の IP | 30 回 / 15 分 | アプリ（同上） |
| ログインと新規登録 | Supabase に届く送り元の IP | 30 回 / 5 分（手元の `config.toml`。本番はダッシュボードの Rate Limits） | Supabase Auth |
| トークンの更新 | Supabase に届く送り元の IP | 150 回 / 5 分（同上） | Supabase Auth |
| 多要素の番号 | 利用者 | 10 回 / 15 分 | アプリ（`/api/auth/mfa`・`/api/account/mfa/verify`） |
| 再設定のメールを送る | メールアドレス・IP | 3 回 / 時・10 回 / 時 | アプリ（`/api/auth/reset-link`） |
| 再設定の番号 | メールアドレス・IP | 5 回 / 15 分・20 回 / 時 | アプリ（`/api/auth/recovery/verify`） |
| キオスクの PIN | 店舗 | 5 回の失敗で 15 分ロック | アプリ（`lib/baggage/kiosk-pin.ts`） |
| エッジの登録（設置コード） | IP | 30 回 / 時 | アプリ（`/api/edge/enroll`） |

- ログインはサーバから Supabase Auth を呼ぶため、**Supabase の IP の制限は Vercel の送り元の IP で数えます**（利用者の IP ではない）。利用者ごと・送り元ごとの制限はアプリで持ち、Supabase の制限は全体の上限として働きます。同じ時間に大勢がログインして 429 が出るときは、ダッシュボードの値を上げます。
- 制限を超えたら 429 と「しばらく待ってから」の文を返し、安全の出来事（`rate_limited`・鍵の種類だけでメールや IP は書かない）を記録します。ログインの失敗は `auth.login_failed` で記録します。
- 回数の制限は嫌がらせへの対策で、認証の境界ではありません。DB が答えないときは通します（フェイルオープン・`lib/rate-limit.ts`）。パスワードの照合そのものは Supabase Auth が行い、その上限は残ります。

### 2.2 嫌がらせのロックを防ぐ

**アカウントを閉じるロックは置きません。** どの制限も「一定の時間だけ待たせる」もので、時間が過ぎれば元に戻ります。管理者が解く操作も要りません。

- メールアドレスの制限（10 回 / 15 分）は、他人がそのメールアドレスでわざと間違え続けると、本人も最長 15 分ログインできなくなります。これを受け入れる理由と、抑えの手段:
  - 待ちは 15 分で終わり、アカウントは閉じない（パスワードの変更も管理者の操作も要らない）。
  - 1 つの送り元から試せるのは 15 分で 30 回（3 アカウント分）までで、多くの利用者をまとめて止めにくい。
  - 失敗と制限は安全の出来事として残り、続くときは運営が送り元を確かめて Vercel の Firewall で止める。
  - 多要素を登録した人は、パスワードが漏れてもログインできない。
- キオスクの PIN のロック（店舗ごと 15 分）は、店舗の ID（UUID）を知らないと起こせません。起きた場合も 15 分で戻り、管理者は PIN を作り直せます。
- 多要素の番号の制限は、パスワードを済ませた本人のセッションでだけ数えます（他人が起こせない）。
- CAPTCHA は置いていません（監視の画面の端末に人の操作を求めないため）。送り元を広く散らした総当たりが見えたら、ダッシュボードの CAPTCHA（Turnstile）を入れることを検討します。

## 3. パスワードの決まりと、使わせない語（6.1.2）

- 長さ: **8 文字以上**（Supabase Auth の `minimum_password_length`・画面と管理の API も同じ）。文字の種類の決まりは置かない。
- 定期の変更は求めない。管理者が決めたパスワードは仮のもので、72 時間以内に本人のパスワードに変えさせる。
- 漏えいしたパスワードの照合: Supabase の「Leaked password protection」（HaveIBeenPwned）を本番で有効にする（Pro 以上の機能・§6 の確認事項）。

### 3.1 使わせない語の一覧

G・VMS の一覧（G・VMS のリポジトリの `docs/SECURITY_REVIEW.md` §1.5）にそろえ、クラウドの名前を足します。大文字と小文字は区別しません。

| 種類 | 語 | 断り方 |
|---|---|---|
| 製品・会社の名前 | `gvms`・`g-vms`・`nvms`・`genesis`・`genesisedge`・`intereco`・`reception`・`gvmscloud` | 含んだら断る |
| 推測されやすい語 | `admin`・`administrator`・`root`・`password`・`passwd`・`user`・`guest`・`operator`・`viewer`・`monitor`・`camera`・`kamera`・`security`・`video`・`recorder`・`keibi`・`kanshi`・`bouhan`・`bohan`・`baggage`・`kiosk`・`store`・`tenpo` | 数字や記号を除いた文字の部分がこれだけなら断る（`Admin2026!` など） |
| 利用者のメールアドレス | `@` より前の部分（4 文字以上のとき） | 含んだら断る |

**残（6.2.11）**: クラウドではまだこの一覧で照合していません。パスワードを決める受け口（仮のパスワードを本人のものに変える・再設定・管理者の作成と再発行）に同じ照合を入れるのは別の作業です。一覧を変えるときは、この節と照合の実装と G・VMS の一覧をそろえます。

## 4. 1 アカウントの同時ログイン（7.1.2）

### 4.1 決め

**同時にログインできる数に上限を置きません。** 上限に達したときの動きはありません。

| | 決め |
|---|---|
| 1 アカウントのセッションの数 | 上限なし（端末・ブラウザごとに 1 つ） |
| 映像の同時視聴（ライブと録画の再生） | テナントごとの上限（`session_limits`・既定 5・運営が `/admin/limits` で決める）。超えると新しい視聴を断る（今見ている人は止めない・`start_live_session`） |
| セッションの終わり | 無操作 24 時間・最長 7 日・ログアウト・管理者の「セッションを切る」（`docs/session-policy.md`） |

### 4.2 理由

- 本部の監視は、壁のモニタ・常時表示の PC・持ち歩くスマートフォン（PWA）を同じ担当者のアカウントで同時に使うのが普通です。上限を 1〜2 にすると、別の端末でログインしたときに監視の画面が黙って切れ、発報を見落とします。
- Supabase Auth が持つのは「1 利用者 1 セッション（新しいログインで古いものを切る）」だけで、数を選べません。

### 4.3 代わりの守り

- 映像の同時視聴（ライブと録画の再生）はテナントごとに上限がある（帯域と、アカウントの使い回しの抑え）。1 回の視聴も既定 120 分で止まる。
- 管理者は利用者の編集の画面で、その人の有効なセッションの数を見られ、全部を切れる（`user_suspension_states`・`revoke_user_sessions`）。
- ログアウトはその人のすべてのセッションを切る（1 台でログアウトすれば、ほかの端末も切れる）。
- 最長 7 日で必ずログインし直す。

上限を置く場合（案）: 1 アカウント 5 セッションまでとし、6 つ目のログインで最も古いセッションを切る（最も古い端末は次の操作でログイン画面へ戻る）。Supabase には数の設定が無いため、ログインの受け口で `auth.sessions` を数えて古いものを消す形になります。発注者の判断を待ちます（§6）。

## 5. 拠点（G・VMS）へのサインインの許可と refresh トークン（10.4.8・10.4.9・10.7.2）

ログインの一本化（G・VMS のリポジトリの `docs/GVMS_CLOUD_SPEC.md` §9）で、クラウドは拠点の G・VMS に対する発行元（OAuth 2.1・OIDC）です。この節の 24 時間のセッション・許可の期限・取り消しの画面は #428 で入れます。

### 5.1 拠点へ出すもの

| もの | 期限 | 決め |
|---|---|---|
| 認可コード | Supabase の既定（数分）・1 回だけ | PKCE（S256）が必須の公開クライアント |
| アクセストークン（JWT） | 1 時間 | 拠点は署名を確かめて身元と役割（`gvms_role`）を読むだけ。クラウドの画面・API・DB では使えない |
| refresh トークン | **出さない** | 拠点のクライアントは `authorization_code` だけを許す（#410・`lib/edge/gvms-oidc.ts`）。Supabase は許していない grant を断る |
| クラウド側のセッション（OAuth のクライアント向け） | **作ってから 24 時間** | 15 分ごとの `oauth_client_session_purge`（`purge_oauth_client_sessions()`・migration 20261030093100）が消す。refresh トークンも一緒に消える |

- **refresh トークンの終わりの期限（10.4.8）**: 拠点のクライアントには refresh トークンを出しません。それより前に作ったクライアントへ出した分、またはクライアントの設定が誤って戻った場合も、クラウドのセッションごと 24 時間で消すため、どの refresh トークンも 24 時間を超えて使えません。さらに Supabase Auth の最長の期限（7 日）と無操作の期限（24 時間）も、OAuth のクライアントのセッションに効きます。Supabase の OAuth 2.1 Server には、クライアントごとの refresh トークンの期限の設定がありません。そのため、24 時間の期限はアプリ（DB の定期の処理）で持ちます。
- cron が止まった場合は、毎日のパーティションの点検（`/api/cron/partition-health`）が「ジョブがありません」と運営へ知らせます。

### 5.2 許可（同意）の期限と取り消し

- 利用者が同意の画面で承認した拠点は、Supabase が覚え、次からは確認を省きます。**この許可は承認から 90 日（案）で切れます**（`lib/edge/gvms-grants.ts` の `GRANT_MAX_AGE_DAYS`）。Supabase には許可の期限の設定が無いため、同意の画面とアカウントの画面を開いたときに、期限の過ぎた許可を本人の接続で取り消します。拠点へのサインインは必ず同意の画面を通るので、期限の過ぎた許可で入ることはありません。確かめられないとき（一覧を読めない・取り消せない）は承認へ進まずに断ります。
- 同意の画面には、サインイン先（店舗と機器の名前）・アカウント・拠点での役割・渡すもの（メールアドレスと役割）・**許可の期限（日時）**・渡すトークンの有効時間（1 時間・refresh トークンなし）を出します（10.7.2）。
- 利用者は **アカウントの画面 › 拠点へのサインインの許可（`/account/sites`）** で、許可した拠点・許可した日時・期限を見て、拠点ごとに取り消せます（10.4.9）。取り消すと Supabase がその拠点向けのセッションを消し、次のサインインで同意の画面がもう一度出ます。取り消しは管理操作の記録（`admin_audit_log`・`sso_grant.revoke`）に残ります。
- 拠点の画面にすでに入っている分は、取り消してもすぐには終わりません。拠点は自分のセッションを持ち、クラウドへ確かめに来ないためです（拠点のセッションは拠点の決まり・G・VMS のリポジトリの `docs/SECURITY_REVIEW.md` §1.1）。すぐ止めたいときは、拠点の管理者がその拠点で利用者のセッションを切ります。

## 7. 見直し

認証の経路を足す・変えるとき、回数の制限の値を変えるとき、四半期の態勢監査（`docs/security-assessment.md`）のときに見直します。この文書の値は実装の定数と同じにします（変えるときは両方を直す）。
