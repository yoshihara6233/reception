# Intereco スケール計画（実数版）

作成: 2026-06-13 / 前提: [wbs-dev-test-plan.md](./wbs-dev-test-plan.md) を本入力で実数化。

## 0. 確定した前提

| 項目 | 値 |
|---|---|
| 体制 | 3〜5名 / 最優先=品質・運用安定 |
| マイルストーン | 2026/11: **1店 / 同時3**、2026/12: **100店 / 同時10**、2027/02: **1000店 / 同時100**、2027/06: **5000店 / 同時300** |
| 店舗上り帯域 | **10 Mbps** |
| NVRベンダ | **Uniview / i-PRO / Frigate** 3つ確定 |
| データ保持 | **31日** |
| reception | **停止確定**（関連リソース整理対象） |

**重要な観察：同時視聴は店舗数の 6〜10% 程度と低い。** システム負荷・コストは「店舗数」ではなく「**同時視聴数（最大300）**」で決まる（オンデマンド方式の前提）。

## 1. 容量・帯域設計

### 1.1 1ストリームあたり帯域（実測ベース）
| 種別 | 内容 | 概算帯域 |
|---|---|---|
| 高画質MJPEG | 720p@5fps、1フレーム約35KB | **~1.5 Mbps** |
| 16/4分割グリッド | 合成JPEG 0.5fps（2秒に1枚） | ~0.3 Mbps |
| 軽量ライブ | 1カメラ 1fps スナップ | ~0.3 Mbps |

### 1.2 店舗上り10Mbpsの収容
- 高画質1本=1.5Mbps。**1店で同時3視聴（11月目標）= ~4.5Mbps + グリッド0.3 ≒ 5Mbps**。10Mbps内に十分収容。✅
- 同一店の高画質同時視聴は実質**最大5〜6本**まで（10Mbps）。通常は1〜数本なので問題なし。

### 1.3 クラウド負荷（同時視聴数ドリブン）
ピーク同時視聴の集約egress（高画質想定）:
| 時期 | 同時 | 高画質ピークegress | 備考 |
|---|---|---|---|
| 2026/11 | 3 | ~4.5 Mbps | 直結トンネルで対応可 |
| 2026/12 | 10 | ~15 Mbps | 軽い |
| 2027/02 | 100 | ~150 Mbps | SFU推奨 |
| 2027/06 | 300 | ~450 Mbps | SFU必須 |

> 実際は高画質は「詳細確認時のみ」で、同時視聴の多くは軽量/グリッド（~0.3Mbps）。上表は高画質最大の上限値。

### 1.4 ストレージ・保持31日
- グリッド/スナップは**上書き**（蓄積なし）。
- **VOD/録画クリップ**＝オンデマンド生成→31日保持→自動削除（cron `/api/admin/vod/cleanup` を31日基準に）。
- 録画本体は現地NVRが保持（31日設定）。クラウドは「視聴/書出した分」のみ＝蓄積は限定的。
- 概算：5000店で月数百GB〜数TB（利用次第）。ライフサイクル削除を必須化。

## 2. アーキテクチャ判断（マイルストーン別）

**ルーティン監視（16/4分割・軽量ライブ）はすでに Supabase Storage 経由で集中化済み＝5000店までスケール可（オンデマンドuploadのみ）。** 課題は**高画質（低遅延）の配信方式**のみ。

| 時期 | 店舗 | ルーティン監視 | 高画質 | 判断 |
|---|---|---|---|---|
| 11月 | 1 | Storage（済） | **Cloudflare Tunnel+MJPEG**（済） | 現状維持 |
| 12月 | 100 | Storage（スケール可） | SFU **ベータ**（10同時は軽い） | SFU早期投入。店舗ごとトンネル自動化は**作らない**（使い捨て回避） |
| 2月 | 1000 | Storage | **SFU 本番**（100同時） | 1000トンネルは非現実的→SFU必須 |
| 6月 | 5000 | Storage（CDN化検討） | SFU スケール（300同時） | SFU水平分散・監視 |

### 判断A：高画質は SFU（クラウドリレー）へ早期移行
- 店舗ごとトンネルは **1店PoC（11月）限り**。100店以降は作らず、**SFUへ集約**（店舗inbound開放ゼロ・NAT越えはクラウド・オンデマンド配信）。
- **初期は LiveKit Cloud（マネージド）** で時期厳守。コストが見えたら自前SFU(LiveKit OSS/mediasoup)へ移行検討（egress単価を下げる）。

### 判断B：ルーティン監視は Storage 継続、5000店でCDN前段
- グリッド/スナップは安価。5000店規模で Supabase egress が増えたら **CDN（Cloudflare）前段**でコスト/負荷を平準化。

## 3. コスト概算（月額・ピーク高画質前提・要検証）

1.5Mbps=0.675GB/時。平均同時≒ピークの1/3、8h/日×22日=176h と仮定。

| 時期 | 平均同時(高画質) | 月egress | LiveKit Cloud(~$0.12/GB) | 自前SFU(~$0.05/GB)+VM |
|---|---|---|---|---|
| 12月(100店) | ~3 | ~0.36TB | ~$45 | VM数千円〜 |
| 2月(1000店) | ~33 | ~3.9TB | ~$470 | ~$200+VM |
| 6月(5000店) | ~100 | ~11.9TB | ~$1,400 | ~$600+VM |

- 実利用は上限より小さい見込み（高画質は一時的）。**マネージドで開始→量で自前移行**が損益的に妥当。
- 別途：Supabase（DB+Storage+egress）、Vercel、ログ/監視基盤の固定費。

## 4. 改訂マイルストーン（4日付に整合）

> 現在 2026/06。11月まで約5か月で「1店の本番品質＋基盤」、その後**月次で10〜50倍**の急拡大。**同時視聴が低い**のが救い。

### M-Nov（2026/11）1店 / 同時3 ― 本番品質＆基盤
- 完了済み：本番公開・リモート高画質・認証・再起動耐性。
- 追加（WBS2/3/4）：**CI/テスト基盤・監視/SRE・環境分離・鍵運用同期自動化・レコーダ管理UI**。
- ベンダ：Uniview/Frigate のライブ・VOD、**i-PRO ライブ**。
- 受入：1店で全機能UAT合格・無人再起動復帰・監視/アラート稼働。

### M-Dec（2026/12）100店 / 同時10 ― 量産＆SFUベータ
- **エッジ量産**（SD/Ansible・初期設定自動化）、**店舗オンボード**（CSV/カメラ割当）。
- **SFUベータ（LiveKit Cloud）**で高画質を集約（10同時は容易）。
- **i-PRO ONVIF Profile-G（VOD）** 投入（3ベンダ確定のため）。
- 受入：100店が手順で構築・グリッド/軽量/高画質(SFU)が安定・31日保持稼働。

### M-Feb（2027/02）1000店 / 同時100 ― SFU本番＆運用自動化
- **SFU本番化**（100同時・トークン制御・オンデマンド配信）。
- 運用自動化（死活監視・アラート・OTA下地・サポート窓口）。
- **負荷試験**（1000エッジ模擬・100同時）。脆弱性診断。
- 受入：1000店で SLO 達成（grid≤2s, ライブ初フレーム≤3s, エラー<1%）。

### M-Jun（2027/06）5000店 / 同時300 ― 大規模・最適化
- SFU水平分散・**グリッドCDN前段**・コスト最適化（自前SFU検討）。
- 大規模運用（オンコール・キャパシティ管理・自動復旧）。
- 受入：5000店・300同時で SLO 維持・コスト目標内。

## 6. スケジュールリスク（率直な評価）

- **タイムラインは非常に意欲的**：1店(11月)→100(12月)→1000(2月)→5000(6月)。特に**12→2月の100→1000**と**量産・SFU本番の同時進行**が山。
- 緩和：
  - **同時視聴が低い**ためクラウド負荷/コストは現実的（最大300同時）。
  - **マネージドサービス活用**（LiveKit Cloud / Supabase / Cloudflare）で内製を最小化し時期厳守。
  - **徹底した自動化**（エッジ量産・オンボード・プロビジョニング）が成否を分ける。
  - 1000〜5000店フェーズは**人員増（5名超）・サポート体制**の検討を推奨。
- 重大リスク：エッジ量産/サポートの運用負荷、SFU本番品質、i-PRO ONVIF難航、店舗回線の実帯域ばらつき。
