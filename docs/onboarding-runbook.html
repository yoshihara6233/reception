0はじめに — 前提と用語

Intereco Monitor は Next.js（Vercel）＋ Supabase（東京）＋ 現地エッジ（Beelink）で動く、既存NVRを活かした録画モニタリング基盤です。手荷物検査はその1モジュールです。録画・物体検知はNVRに任せ、エッジは「RTSP取得→合成/ライブ/VOD/検査クリップ→クラウド配信」だけを担う軽量構成（②relay）が本命です。

用語意味
テナント契約単位（＝顧客企業）。この配下に店舗・ユーザー・エッジがぶら下がる。RLSで完全分離。
② relay / 中継ユニット店舗に置く小型PC（N100級・Beelink等）。録画せず中継のみ＝安価・軽量・アウトバウンド通信のみ。本命構成。
エンロールエッジの初回自己登録。本部発行のQR/トークンを現地で読ませ、device_tokenとSFU資格を払い出す。手貼り不要。
OTAエッジの自律自己更新。本部が目標版SHAを宣言→エッジがpull→preflight→切替→健全性確認→昇格 or ロールバック。
baggage_manager手荷物検査の店長ロール。ライブ視聴は不可、/baggage・/kiosk・検査APIのみ許可。

この手順書のスコープ

PoC〜初期店舗を ② relay 構成 で開通する実務に絞っています。① 本部直結 / ③ Frigate録画 はGA後の別構成のため対象外です。DB本体は東京Supabase vywvpcjbicrtcyvzmrwh。

2A. テナント開通手順（本部→現地）

super_admin（本部）が主体。手荷物検査を使う店舗を「ゼロから使える」状態にするまでの7ステップです。

#手順実施場所 / 実体状態
1 テナント作成 ＋ テナント管理者ユーザー作成
契約単位を作り、その管理者を1名用意する。		 super_admin が tenants とユーザーを SQL / seed で直接作成（専用UIなし）。 UI未整備
2 店舗の登録
name / 住所 / 緯度経度 / timezone / tenant_id。		 /admin/stores（既存編集）または CSV一括インポート POST /api/admin/import/stores。 新規フォーム無
3 エッジ登録（②relay）
エッジ行を作り、現地に渡すQR/トークンを発行。		 /admin/edges/new → 構成 relay ＋ tier(16/32/48) ＋ 名前 → edge_devices行 ＋ エンロールトークン発行 → QR表示。 実装済
4 NVR / カメラ登録
現地Beelink構築（B）後、ウィザードで接続確認まで。		 NVR接続(host/creds) → ONVIF自動探索 → ch列挙 → grid割当(0–15) → 接続テスト（RTSP/snapshot到達＝緑）。 実装済
5 キオスクPIN発行
iPadを店舗に紐づけるログイン情報。		 /baggage/ipad で店舗別6桁PIN＋QR発行 → iPadでPINログイン。 実装済
6 従業員の顔登録・同意設定
退室時の顔照合に必須の元データ。		 管理UIで従業員登録＋顔登録（同意記録）。来訪者同意文言・入退室あいさつ文言は /admin/baggage で編集。 事前完了が前提
7 iPad 実機E2E
現場で入室/退室が一巡することを確認。		 PWA「ホーム画面に追加」→ 店舗キオスクが起動 → 入室（顔撮影）/退室（顔認証＋手荷物検査）疎通。 再読込必須

⚠️ A-6 の要注意点 — 顔登録は開通の前提

開通前に 全従業員の顔登録が完了していないと、退室照合がすべてアンマッチになります（バグではなく元データ不足）。店舗ごとに「従業員名簿 → 顔登録 → 件数突合」を開通チェックリスト（§4）で必ず消し込むこと。

店舗CSVインポートの形（A-2）

3B. Beelink 構築手順（②中継ユニット）

🔴 実機のサービス名は intereco-edge

配布テンプレート（edge-agent / node dist / ユーザー edge）とは別構成です。PoC実機は Bun直実行・ユーザー intereco・Frigateは同居Docker。systemctl status edge-agent は "Unit not found" になります。必ず intereco-edge を使うこと。

#手順内容
1 ハード Beelink Mini-S（Intel N系 iGPU / QuickSync）。本番本命は産業用ファンレスN100・16GB・2NIC。録画/検知はNVR任せで軽量。
2 OS / 前提 Ubuntu。ffmpeg、Bun（/home/intereco/.bun/bin/bun）。実行ユーザー intereco（home /home/intereco）。
3 エージェント配置 リポジトリ配置 → bun install → agent.env 作成（Supabase URL/anon、MONITOR_URL 等。device_token は §7エンロールで払出）。
4 systemd 常駐 /etc/systemd/system/intereco-edge.service → enable --now。状態・ログは下のコマンド参照。
5 Cloudflare Tunnel cloudflared-intereco 常駐。高画質固定URL poc-beelink.genesis-edge.com ＋ Cloudflare Access（許可メール制）。go2rtc公開オリジンを配下カメラが継承。
6 Frigate（必要時のみ） 同一Beelink上のDockerで常駐（docker ps/restart/logs -f frigate）。②relayでは基本不要。
7 エンロール A-3のQR/トークンを読取 → POST /api/edge/enroll{token} → device_token ＋ SFU資格を払出（単一使用・TTL・テナント/店舗束縛を検証）。
8 OTA 自己更新 本部が desired_agent_version（gitショートSHA）を宣言 → 約5分でpull → preflight → 切替 → 健全性（再起動後90秒以内heartbeat＋90秒安定）→ 昇格 or 既知良好版へロールバック。
9 疎通確認 16分割グリッド／単一ライブ／VOD取得／手荷物検査クリップ切出し を intereco-edge ログで確認。

実機の運用コマンド（Beelink に SSH 後）

sudo systemctl status  intereco-edge          # 状態確認
sudo systemctl restart intereco-edge          # 再起動（必要時のみ）
sudo journalctl -u     intereco-edge -f          # ログ追尾（q で抜ける）
sudo journalctl -u     intereco-edge -f -o cat   # JSON ログを全幅表示

docker ps | grep frigate     # Frigate 稼働確認（同居時）
docker restart frigate       # Frigate 再起動

※ SSH・エッジ操作は現地担当（人）が実行。本手順書はコマンドを提示するのみ。

B2AI201 本番機セットアップ手順（実機確定機）

本番機を AIOPCWA AI201 に確定（2026-07-23 購入）

②中継ユニットの本番候補として AIOPCWA AI201（Intel N100・ファンレス・2×2.5GbE i226V・16GB / 256GB・RS232/485・7/24無音）を採用。Amazon.co.jp B0D44SVY8S。本節は上の B 手順をこの機に合わせて具体化したもの。選定根拠は docs/edge-configs-and-relay-hardware.md §2-B。

🔴 この機の固有ポイント（先に押さえる）

  • プリインは Windows 11 Pro → Ubuntu を上書きインストール（用途はUbuntu relay。Windowsは使わない）。
  • NIC が新しめの i226-V（2.5GbE×2） → カーネルの新しい Ubuntu を使う（22.04.4 以降 もしくは 24.04 LTS）。古いISOだと NIC 認識で詰まる。
  • ファンレス筐体 → 放熱スペースを確保（積み重ね・密閉を避ける）。24/7 で温度を監視。
  • 当面 Tier S＝最大16カメラなので 2.5GbE は1口（WAN）で成立。将来カメラ網を分離するとき2口目を使う。
#手順内容（AI201 具体）
1 開梱・設置 放熱スペース確保して設置。LAN を enp*(2.5GbE) の1口目に接続。電源投入。(所要15分)
2 Ubuntu 上書き USBインストーラ（Ubuntu 24.04 LTS 推奨）で Windows を上書き。ユーザー intereco（home /home/intereco）を作成。SSH有効化。
3 iGPU / NIC 確認 ここを最初に緑にする。QuickSync(VAAPI)と 2.5GbE×2 の認識を下のコマンドで確認（詰まりの主因を先に潰す）。
4 前提パッケージ ffmpeg と Bun（/home/intereco/.bun/bin/bun）を導入。
5 エージェント配置 リポジトリ配置 → bun install → agent.env 作成（Supabase URL/anon・MONITOR_URL 等。device_token は §7 エンロールで払出）。
6 systemd 常駐 /etc/systemd/system/intereco-edge.service → enable --now。サービス名は必ず intereco-edge。
7 Cloudflare Tunnel cloudflared-intereco 常駐。高画質固定URL＋Cloudflare Access（許可メール制）。§B-5 と同一手順。
8 エンロール A-3 の QR/トークンを読取 → device_token ＋ SFU資格を払出。
9 疎通＋ベンチ 16分割／単一ライブ／VOD取得／検査クリップを確認。同時に下のベンチ観点で §2-B 選定チェックを消し込む。

#3 の確認コマンド（iGPU QuickSync ＋ 2.5GbE）

# QuickSync(VAAPI) が見えるか
sudo apt update && sudo apt install -y intel-media-va-driver vainfo intel-gpu-tools
ls -l /dev/dri/renderD128           # 存在すること
vainfo                              # H264 / HEVC の Encode/Decode エントリが出ること

# 2.5GbE(i226-V) が2口とも見えるか
ip -br link                         # enp* / eth* が2つ（2.5GbE×2）
ethtool enp1s0 | grep -i speed      # 2500Mb/s でリンクすること（口名は環境依存）

※ /dev/dri/renderD128 が無い／vainfo がエラー＝VAAPI未設定。ここが緑にならないと合成/ライブ/VODが CPU 処理に落ちて重くなる。先に解決してから #4 以降へ。

#9 のベンチ観点（§2-B 選定チェックの消し込み）

  • 16ch合成(0.5fps)＋高画質ライブ1本＋VOD1本 同時を回して安定表示
  • iGPUデコード負荷を intel_gpu_top で確認（合成がHWデコードに載っている）
  • 筐体温度を sensors で継続監視＝サーマルスロットリングが起きない（ファンレスの要）
  • 24時間連続で heartbeat 安定・プロセス無再起動
  • （可能なら）ワットチェッカーで消費電力を実測

満たせば「N100 / 16GB / 2NIC の1SKU」を本番SKUとして確定（edge-configs-and-relay-hardware.md §2-B へ結果を反映）。

B3時刻同期（NTP）標準構成 — エッジ＝店舗の時刻源

🔴 なぜ必須か（2026-08-01 実弾BCPの教訓）

BCP・発報前コマ・検査クリップはすべてNVRのタイムラインから切り出すため、NVRの時計ズレがそのまま証跡に乗る（実例: NTP未設定のNU101が+3分進み、電波時計と映像の取得時刻が食い違った）。i-PRO NVRの公開CGIに時刻を書き込むAPIは存在しないため、NTPが唯一のプログラマティックな時刻補正手段。開通時に必ずこの節を消し込む。

標準構成: エッジ（Beelink/AI201）に chrony を立てて店舗LANのNTPサーバにし、NVR・カメラはエッジを参照する。エッジ自身は Ubuntu 標準の chrony がインターネットの公開NTP（Canonical プール）に常時同期（64秒〜約17分の適応間隔・ズレは常時ミリ秒単位）。これにより NVR/カメラがインターネットに出られないLANでも時刻が揃う。

手順（エッジ側 — SSH で3分）

# 1) chrony 導入（Ubuntu は大抵プリイン。念のため）
sudo apt-get install -y chrony

# 2) 店舗LANセグメントへの配信を許可（★セグメントは店舗に合わせる）
echo 'allow 192.168.0.0/24' | sudo tee -a /etc/chrony/chrony.conf

# 3) ファイアウォール開放（ufw 有効機は必須 — これを忘れると無応答）
sudo ufw allow 123/udp

# 4) 反映
sudo systemctl restart chrony

検証（LAN内の別マシンから）

sntp <エッジIP>          # macOS の例。Linux は chronyc / ntpdate -q
# → 「-0.023632 +/- 0.234156 192.168.0.100」のような1行が返ればOK
  • 「Exchange failed: Timeout」 → ufw で UDP 123 が塞がっている（手順3）。
  • 「Server not synchronized」 → chrony 再起動直後で上位と同期中。1〜2分待って再実行。

機器側の設定

機器設定
i-PRO NVR（NU101等）設定画面 → 日時 → NTP を「使用する」、サーバアドレス＝エッジのLAN IP。タイムゾーン JST を確認。
カメラNVR の NTP 配布機能があれば NVR 参照、なければ各カメラの NTP をエッジIPに。OSD 表示時刻が揃うことを目視確認。
エッジ本体設定不要（Ubuntu 既定で公開NTPに常時同期）。chronyc tracking で Stratum 3 前後・Ref time が現在時刻なら健全。

設計メモ

  • ネット断時の挙動: chrony は上位と同期できない間、既定では「未同期」として配信を止める（誤時刻の拡散防止）。長期オフラインでも配信を続けたい店舗のみ local stratum 10 を chrony.conf に追記（自走時計を配る設計判断。通常は不要）。
  • 実績: 2026-08-02 beelink-demo + NU101 で実証（+3分ズレ → 公共NTPで±6秒 → エッジ配信構成へ切替）。Mac からの検証値 -0.02秒。
  • 時刻設定APIについて: i-PRO 公開CGI（httpdl / recordedtime / as_getinfo / snapshot）に時刻設定は無い。設定画面裏の非公開CGI直叩きはFW更新で壊れるため禁止。外部からの時刻設定/オフセット取得APIの有無は i-PRO 面談 Q7 で確認中。

6トラブル初動 — よくある落とし穴

症状真因初動
OTAが更新されずロールバックになる 目標版SHAに末尾スペース混入 → git worktree add が invalid reference → 恒久 stage_failed → cooldownで同SHA再指定もスキップ 空白なしで再入力（別文字列扱いでcooldown回避）。入力trimは#203で恒久修正済
特定時刻の検査クリップが両カメラとも取得できない i-PRO httpdl.cgi は分単位・秒00固定。同一分内の短い検査窓で START==END → 空応答 → 恒久失敗 iproVodMinuteRange（START分切捨/END分切上）で修正済（#202）。手動「映像を再取得」ボタンも有
退室の顔照合が合わない その人が未登録 or 閾値未達（バグではない） 顔登録の有無を確認。閾値は72で様子見中
iPadに新機能が反映されない PWA SPAのためデプロイ後に自動更新されない アプリを再読込（ホーム画面アイコンから開き直す）
Safariでホーム画面追加すると管理画面が開く 共通manifestの start_url は本部監視用（/stores） 店舗別manifest（#196）で対策済。店舗キオスクURLから追加すること
「確認済み」が動画を見る前に押せてしまう — 再生完了までゲート（#200）で封鎖済。仕様どおり
