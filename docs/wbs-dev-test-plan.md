## 3. テスト計画

### 3.1 テスト戦略
- **テストピラミッド**：単体（多）→ 結合/契約 → E2E（少・主要動線）→ 手動探索/実機（PoCならでは）。
- **シフトレフト**：CI(2.1)でPR毎に typecheck/lint/build/unit を必須化。出口基準を各レベルで定義。
- **実機重視**：NVR/カメラ/トンネル/Access が絡むため、自動化＋現地受入(UAT)を併用。

### 3.2 テストレベルと範囲

| レベル | 対象 | 手法/ツール | 主担当 |
|---|---|---|---|
| 単体 | monitor lib / edge 状態機械・URL・upload | vitest, RTL | 各開発 |
| 結合 | API↔Supabase(RLS)、API↔edgeコマンド | 統合テスト, テストSupabase | Backend |
| 契約 | コマンド/テーブルスキーマ整合 | スキーマ検証 | Backend |
| E2E | login→監視→グリッド→ライブ→VOD | Playwright/gstack | QA |
| 性能/負荷 | 10,000エッジ模擬・100同時視聴・grid更新 | 負荷生成・k6/カスタム | SRE |
| セキュリティ | RLS越権・公開面・鍵・Access | 診断・手動・自動 | Sec |
| 受入(UAT)/実機 | 実店舗で全機能・体感品質 | 現地チェックリスト | PM+運用 |
| 回帰 | リリース前必須セット | 自動+手動チェックリスト | QA |

### 3.3 性能・負荷テスト（重点）
- 目標値（要確定）例：grid JPEG 更新 ≤2s、ライブ初フレーム ≤3s、同時視聴100でエラー率 <1%。
- シナリオ：エッジ大量 heartbeat、同時 start_grid/start_live、VOD同時、トンネル/SFU帯域。
- 環境：staging + エッジ模擬（コンテナ多重起動）。

### 3.4 セキュリティテスト
- RLS：各ロール/テナントで越権不可を自動検証（8.1）。
- 公開面：未認証で poc-*.genesis-edge.com が 302 ブロックを継続監視（8.3）。
- 鍵：ローテ後の旧鍵失効・edge同期を検証（4.1/8.2）。
- 外部診断：パイロット後に実施（8.4）。

### 3.5 受入(UAT)・実機テスト
- 店舗チェックリスト：16分割/4分割/単一ライブ/高画質(ローカル/リモート)/VOD/BCP/アラート地図/再起動復帰。
- 体感品質：遅延・コマ落ち・回線細時の劣化挙動。

### 3.6 テスト管理
- **入口基準**：対象機能の実装完了・単体緑・テストデータ準備。
- **出口基準**：重大/高 残不具合ゼロ、回帰緑、性能目標達成、UAT承認。
- **カバレッジ目標**：重要lib 70%+（数値は運用で調整）。
- **不具合管理**：重大度(Blocker/Critical/Major/Minor)・再現手順・回帰登録。

### 3.7 CI/CD パイプライン（出口ゲート）
```
PR     : typecheck + lint + build + unit (+ 契約)        … 必須緑
merge  : E2E(主要動線) on staging
release: 回帰スイート + 性能スモーク → 本番デプロイ → canary監視
```

## 7. 要確認事項（計画精緻化のための入力）

1. 目標時期・予算（特に M4 パイロット時期、SFU移行の予算枠）。
2. 対象店舗数・1店あたりカメラ数・想定同時視聴数（性能目標の確定）。
3. 店舗回線の上り帯域の実態（高画質方式の選定）。
4. 認証/IdP の方針（メールOTP継続か、企業IdP/SSO導入か）。
5. NVRベンダの確定（Uniview/i-PRO/Frigate の優先度）。
6. データ保持/コンプライアンス要件（録画保持期間・アクセス記録）。
7. 既存 reception の扱い（停止確定なら関連リソース整理）。

これらが確定すると、各WPの工数・スケジュール・コストを実数化できる。
