# エッジ構成 3種 と 中継ユニット(②)ハード設計

作成: 2026-06-13 / 前提: [decision-sfu-and-edge.md](./decision-sfu-and-edge.md)（SFU=LiveKit Cloud 承認）

## 0. 構成3種（基本形）

| 構成 | 名称 | 拠点ハード | 録画 | 中継処理の場所 | 位置づけ |
|---|---|---|---|---|---|
| **①** | 既存NVR + **中継ユニットなし**（本部直結） | **なし**（NVRのみ） | 既存NVR | **本部サーバが直接NVRから取得** | 拠点に機器を増やさない構成。帯域/接続に制約（§1.5） |
| **②** | 既存NVR + **中継ユニット** | **中継ユニット(軽)** | 既存NVR | **拠点の中継ユニット** | **メイン構成** |
| **③** | Frigate（録画+中継） | **録画ユニット(重)** | ユニット(Frigate) | 拠点ユニット | レコーダ無し顧客向け。**稀** |

**設計の含意：**
- **②は録画も検知も既存NVRに任せる**ため、中継ユニットは「**RTSP取得→グリッド合成/スナップ/VOD取得→クラウド配信**」だけ。**録画ストレージ不要・物体検知不要＝軽量・安価**。
- ③は録画(31日)を自前で持つため**大容量ストレージ＋検知用の処理能力**が必要＝高価・大型。だから「稀」。
- ①は拠点機器ゼロだが、**中継処理を本部側で行う＝NVRから本部へ映像を送る必要があり、帯域・接続・セキュリティに制約**（次節）。

### 0.5 構成①（本部直結）の詳細と制約

拠点に中継ユニットを置かず、**本部サーバが店舗の既存NVRに直接接続**して中継処理（グリッド合成・スナップ・VOD・SFU配信）を**本部側で**行う。

**メリット：** 拠点に機器を増やさない（ハード費・設置ゼロ）。

**制約（重要）：**
| 論点 | 内容 |
|---|---|
| **上り帯域** | 本部がNVRから**RTSPを引く**＝店舗の上り10Mbpsを消費。フル解像度は1ch2〜4Mbps→**多カメラ合成は10Mbps超で不可**。**サブストリーム(低解像)やNVRのモザイク出力**なら可だが画質/機能に制限 |
| **接続性** | 本部がNVRに**到達**する必要＝NVRの**ポート開放/VPN/ベンダP2Pクラウド**(Uniview EZCloud, i-PRO)等。②は**アウトバウンドのみ**で不要 |
| **セキュリティ** | NVRをWANに晒す/外部到達を許す面ができる（②は開放ゼロ） |
| **本部の処理負荷** | 合成/トランスコードを**本部で集中**＝同時視聴店舗数に比例して**クラウド計算コスト増** |
| **適性** | **カメラ少数**の店舗、機器を置けない/置きたくない顧客、NVRが使えるモザイク/P2Pを持つ場合に向く |

→ **①は「少カメラ・機器レス希望」向けの限定構成**。②（中継ユニット）は**上り帯域を桁違いに節約（合成JPEGを~0.3Mbpsでアップ）・アウトバウンドのみで安全・本部負荷も小**なので、**多カメラ/標準はやはり②が本命**。

### 3構成 比較マトリクス
| 観点 | ① 本部直結 | ② 中継ユニット(本命) | ③ Frigate録画 |
|---|---|---|---|
| 拠点ハード費 | ◎ ゼロ | ○ ¥1.5〜3万 | △ 多TB機・高価 |
| 上り帯域効率 | ✕ NVRからフル/サブを引く | ◎ 合成JPEG~0.3Mbps | ◎ 同上 |
| 接続/セキュリティ | △ NVR到達要(開放/VPN/P2P) | ◎ アウトバウンドのみ | ◎ |
| 本部計算負荷 | △ 集中(同時数に比例) | ◎ 分散(拠点) | ◎ |
| カメラ多数(〜16) | ✕ 帯域で困難 | ◎ | ◎ |
| 録画 | 既存NVR | 既存NVR | ユニット(31日要ストレージ) |
| 適性 | 少カメラ/機器レス | **標準・多店舗** | NVR無し(稀) |

### 0.6 構成①の現実解：VPN + VGA JPEGスナップ壁（10秒/枚）

①は **VPN前提**（本部⇔店舗LAN）。**全カメラ常時ストリーミングはやめ**、本部が各カメラの**JPEGスナップを10秒毎に取得して16分割表示**する方式が現実的。

**帯域試算（16カメラ）：** VGA JPEG ~40KB × 0.1fps × 16ch = **~0.5Mbps**（10Mbps上りに余裕）。

| 項目 | 設計 |
|---|---|
| 概況(16分割) | 本部が **ONVIF/HTTPスナップ**(無ければRTSPキーフレーム1枚)を**10秒毎**取得 → 16分割合成。VGA(640×480) |
| 詳細(単一) | タップで**その1台だけ**ライブ取得（サブストリーム~1Mbps）。同時は1〜数台に限定 |
| 帯域 | 概況~0.5Mbps + 詳細1台~1Mbps ＝ 10Mbpsに十分収まる |
| リフレッシュ | 既定10秒（設定可。少カメラ時は短縮可） |
| 取得元 | NVR/カメラのスナップ endpoint（Uniview/i-PRO とも対応。VPNでLAN到達） |
| 実装 | 既存 edge-agent の**グリッド/スナップ取得ロジックを本部側で“仮想エッジ”として実行**（NVRをVPN越しに参照）。オンデマンド（視聴時のみ） |

→ **この方式で①の帯域制約は実質解消**。①の `上り帯域効率` は ✕→**○（スナップ壁なら良好。多台同時ライブは△）** と再評価。**概況はスナップ壁・詳細は単一ライブ**という割り切りが鍵。

## 1. ② 中継ユニットの役割（ソフト構成）

中継ユニットがやること（録画はしない）:
1. 既存NVR(Uniview/i-PRO)の **RTSPチャンネルを取得**（go2rtc で再ストリーム集約）。
2. **16/4分割グリッド**：ffmpeg で各chスナップを合成JPEG化 → Supabase Storage へ（0.5fps）。
3. **軽量ライブ**：1ch スナップを1fpsでアップロード。
4. **高画質**：go2rtc/WHIP で **LiveKit Cloud(SFU) へ publish**（オンデマンド）。
5. **VOD**：Uniview replay RTSP / i-PRO ONVIF Profile-G から区間取得 → アップロード。
6. heartbeat・コマンド受信（Supabase Realtime）・自己更新(OTA)。

> **Frigate は使わない**（録画/検知はNVR）。**go2rtc を中核**に据える。現行 edge-agent の「ベンダ直RTSP経路(Uniview/i-PRO)」を主経路化する小改修が必要（§4）。

### 処理負荷の見立て（②）
- グリッド合成は **0.5fps**（2秒に1枚）。16ch同時デコードでも軽い（**Intel iGPU QuickSyncのHWデコード**前提）。
- 高画質publishは通常 **1〜数ch**。
- **物体検知なし**＝GPU/Coral不要。CPUは省電力級で十分。

## 2. ② 中継ユニット ハード仕様（推奨）

**クラス：Intel N100級 ファンレス x86 ミニPC（QuickSync内蔵）**

| 項目 | 推奨 | 理由 |
|---|---|---|
| CPU | **Intel N100 / N97 / N305**（Alder Lake-N, UHD iGPU） | 多chのH.264/H.265 **HWデコード**。省電力(6〜15W) |
| RAM | **8GB**（16GBで余裕） | 中継のみ。検知なし |
| ストレージ | **64〜128GB SSD/eMMC** | OS+一時のみ。**録画しない**ので小容量 |
| NIC | **2×GbE 推奨**（1でも可） | カメラ用LANとWANを分離（セキュリティ/帯域） |
| 形状 | **ファンレス**（産業/DIN対応だと尚良） | 24/7・店舗環境(埃/熱) |
| 電源 | ACアダプタ（小型）/ 一部PoE | 省電力 |
| 概算単価 | **¥15,000〜30,000**（民生）/ ¥40,000〜（産業ファンレス） | 量産調達 |

- **市販で代理店が調達可能**な N100 ミニPC（多ブランド）。**デュアル/クアッドNIC版**（ファイアウォール用途で普及）はカメラVLAN分離に好適。
- PoCのBeelinkも N系iGPUなので**②の検証はそのまま流用可**。本命は**産業用ファンレスN100**を1〜2機種、実機評価（実負荷/温度/供給安定）。

### ストレージ容量（②は小、③は大）
- **②：録画なし** → 64〜128GBで十分。
- **③（参考）**：録画 = カメラ数 × ビットレート × 31日。例) 8ch×4Mbps×31日 ≒ **約10TB/月**（H.265・動体録画で大幅減）。→ **多TB SSD/HDD必須＝高価**。③が「稀」な理由。

## 3. 代理店による購入＋設定（ゼロタッチ志向）

目標：**代理店が機器を購入し、設定まで完了**できる。技術が深くなくても可。

### 3-1. ハード調達
- **承認機種リスト**（N100ファンレス x86 の推奨2〜3モデル＋スペック表）を配布 → 代理店が市販ルートで購入。
- もしくは**当社が事前イメージ済みユニットを販売/貸与**（最も確実）。

### 3-2. 設定（ゴールデンイメージ + 初回ブート登録ウィザード）
1. **事前イメージ**：OS + go2rtc + edge-agent + cloudflared/livekit 一式を焼いた状態で出荷/配布（USBインストーラ or 完成品）。
2. **初回起動でセットアップウィザード**（ユニットのローカルWeb or 当社管理画面）：
   - **店舗コード/ワンタイム登録トークン（QR）**を入力 → クラウドが EDGE_ID・各種鍵・SFU資格情報を払い出し（**鍵ローテも同経路**＝本日の事故を構造的に解消）。
   - **NVR接続**：NVRのIP・ID/PWを入力 → **ONVIF自動探索でチャンネル列挙** → カメラ名/グリッド位置を割当。
   - 接続テスト（RTSP到達・スナップ取得・SFU publish）→ 緑なら登録完了。
3. 完了後は**遠隔管理**（heartbeat/監視/OTA）に載る。遠隔SSHは既存トンネル流用。

### 3-3. 当社が用意するもの（WBS）
- 事前イメージ/インストーラ、**初回登録API＋ウィザードUI**、**ONVIF自動探索＋カメラ割当UI**、接続セルフテスト、**代理店向け設定手順書**。
- 承認ハードのスペック表/調達ガイド。

## 4. コードへの影響（②をFrigate非依存にする）

現行 edge-agent はグリッドのスナップを Frigate(`/api/<cam>/latest.jpg`) から取得。**②はFrigate無し**なので：
- **go2rtc 経由のスナップ/再ストリーム**を主経路化（NVRのRTSP→go2rtc→snapshot/MSE/WHIP）。
- グリッド合成(grid.ts)・ライブ(live.ts)・VOD(vod.ts)の**ベンダ直/又はgo2rtc経路**を整備（Uniview/i-PRO）。
- 高画質は **Frigate MSE → go2rtc/WHIP→LiveKit** へ（SFU決定に整合）。
→ WBS5(ベンダ対応) と WBS7(SFU) に統合。i-PRO ONVIF(5.2) も②/③共通で必要。

## 5. 未確定・要入力

1. **構成①の本部→NVR 到達経路**：定義は確定（拠点中継なし・本部直結）。残るは**到達手段**（NVRのポート開放 / VPN / ベンダP2Pクラウド[Uniview EZCloud, i-PRO]のどれを採るか）と、**①の対象カメラ数上限**（上り10Mbpsの制約上、フル/サブで何chまで許容か）。
2. **②の1店あたりカメラ数（平均/最大）**：合成/同時publish/帯域の確定。最大16前提でよいか。
3. **②でも軽い検知(動体等)を載せるか**：載せるなら CPU/メモリを一段上げる（基本は検知なし＝NVR任せ）。
4. **NVR機種の具体**：Uniview/i-PRO の対象モデル（ONVIF/replay の対応確認）。
5. **代理店モデル**：承認機種を代理店調達 か、当社が事前イメージ品を供給 か。
6. ③の録画ストレージ要件（カメラ数×ビットレート×31日）と機種クラス（稀だが仕様は用意）。

## まとめ
- **②（メイン）＝録画/検知はNVR、ユニットは中継のみ → Intel N100級ファンレスx86・8GB・64〜128GB・2NIC・¥1.5〜3万**。安価・省電力・市販調達可。
- **代理店の購入＋設定**は「**承認機種 or 事前イメージ品 ＋ QR初回登録 ＋ ONVIF自動探索ウィザード**」で実現（要・当社側UI/手順整備）。
- ③は録画ストレージが重く高価＝稀。①は定義要確認。
- 最重要入力は **②のカメラ数（最大16でよいか）** と **NVR対象機種**。
