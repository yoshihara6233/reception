主要な「踏んだ罠」と回避策（実装で得た知見）

罠症状対策
macOS AirPlay Receiver が :5000 を専有 Frigate API へ届かず VOD/Snapshot が 403 System Settings で AirPlay Receiver を OFF。または Docker 側で 5050:5000 に remap し FRIGATE_API_PORT 環境変数で逃がす
Frigate の auth.enabled=true HTTP /api/* が 401 dev 環境では config.yml に auth: {enabled: false}。本番は edge 側に Bearer/Cookie 認証実装が必要
LiveKit Cloud の WHIP エンドポイント 素の /rtc/whip?token= は HTTP 200 "OK" を返し ffmpeg が SDP として解釈不能 Ingress API で <proj>.whip.livekit.cloud/w/<streamKey> を毎セッション発行、edge は受け取った URL をそのまま -f whip に渡す
ffmpeg 8.1 の WHIP muxer が TCP ICE 候補で死ぬ LiveKit の SDP answer 先頭の TCP 候補で Protocol tcp is not supported by RTC edge-agent 内に localhost WHIP プロキシを立て、a=candidate:... tcp ... 行をストリップして ffmpeg に渡す
Frigate go2rtc の main stream 不安定 16分割 grid の ffmpeg が起動時の 1 frame だけ取れて固着 v4.0 で JPEG ポーリング化したため無関係化。残存する VOD 経路では go2rtc <cam>_sub ストリーム使用
Supabase Storage CDN が認証エンドポイントもキャッシュ edge は新 JPEG を upload しているのにブラウザは同じ md5 を受け取る cloud route 側で storage URL に ?t=Date.now() を付加してキャッシュバイパス
LiveKit Cloud の Ingress quota（free tier 2） VOD シークごとに ingress 作成 → 数回で 429 /api/livekit/ingress route で同 room の旧 ingress と他 room の INACTIVE を毎回 GC、create 失敗時は 1.5s backoff で 1 回 retry
ffmpeg の -fflags +nobuffer -probesize 32 過剰最適化 RTSP の H.264 SPS/PPS が見つからず "Output file does not contain any stream" で即死 -fflags +nobuffer のみ残し probesize/analyzeduration は default に戻す
HTTP MP4 を -re なしで WHIP に流すと UDP バッファ溢れ Failed to write packet, ret=-55 No buffer space available VOD の Frigate MP4 入力時のみ -re で実時間ペーシング

1. システム仕様書

1.1 システム概要

全国最大 10,000 店舗 に設置された監視レコーダ（i-PRO / Uniview）を、 本部から一元的にリモート監視・録画再生する大規模クラウド統合システム。 オペレータによる実モニタリング時間は 1 日 2 時間以内 を前提とし、 平常時はエッジを待機させる オンデマンド方式 を採用してクラウドコストを最適化する。

本システムを 10,000 店舗規模で成立させる 4 つの設計原則 (v4.0 改訂)
  1. JPEG ポーリング・ファースト: 16分割 / 単一ライブはすべて HTTP JPEG fetch ベース。RTSP→ffmpeg→WHIP→LiveKit の重いスタックは VOD（録画再生）のみに限定し、依存・コスト・障害面を激減
  2. オンデマンド起動: 視聴開始時にのみエッジで JPEG ループを起動。誰も見ていない店舗は完全に待機（CPU・帯域・課金とも最小）
  3. 本部 ≪ 店舗 のトラフィック非対称: 大量の店舗データを集中処理せず、視聴中の店舗 (常時数十程度) のみがアクティブ
  4. マネージド全振り: Vercel + Supabase + LiveKit Cloud で運用人員を最小化し、10,000 店舗規模でも 1 名運用を目標

BCP Mode（J-Alert クリップ録画） 事象発生 -3min〜+5min の MP4 を全 ch 並列で取得（uniview RTSP / Frigate clip.mp4）、Storage bcp-clips に PUT、サムネは Frigate API JPEG 10〜30%（一時的） Storage PUT（一時バースト）
Snapshot Mode（SECURITY 巡回・一発撮り） capture_snapshot 受信 → 指定 ch の latest.jpg を取得 → cloud の /api/security/patrol/ingest へ multipart POST（Bearer device_token） 1〜2%（一瞬） HTTP POST のみ

v3.0 から v4.0 への JPEG ポーリング移行により、grid / live モードでの LiveKit 課金が完全に消滅。 LiveKit 利用は VOD 視聴時のみとなり、月間ストリーム時間が 1/10 程度に圧縮される見込み。 オンデマンド方式と組み合わせて、平均モニタリング時間 1 日 2 時間 × 30 オペレータの想定で、 クラウドコストを v3.0 比でさらに 30〜40% 圧縮。

7.3 INFRA 死活監視

7.3.1 概要

edge_devices.last_seen_at から 5 分閾値で offline を検知して monitor_incidents に起票。 テナント内の店舗の ≥60% が同時 stale なら個別 edge_offline ではなく tenant 単位の network_outage として 1 件起票（一斉障害でアラートが溢れない設計）。

7.3.2 無人ストリーム watchdog

v4.0 で追加された monitor_sweep_unattended_streams() 関数（pg_cron 毎分）:

  • Case 1: status ∈ (grid,live,vod,bcp) かつ heartbeat が 3 分以上停滞 → status を offline に補正
  • Case 2: status ∈ (grid,live,vod) かつ pending_command_at が 90 分（= LiveKit token TTL 上限）超 → stop_stream を自動発行
  • Case 2 を発行した行は monitor_incidents に stream_autostopped（info, resolved）として監査記録（CTE で UPDATE と INSERT を 1:1 連結）

v4.0 は「各店舗 Mini PC + Frigate」前提だった。これは 10,000 店舗で 1 店舗 ¥80,000 × 10,000 = ¥8 億円 の初期投資が必要。 既に NVR が入っている店舗ではこのハードを 重複導入 することになる。

v5.0 で 中央集約モード (Tier 3) を追加し、既存店舗 NVR を直接 API で叩く構成を実装。 店舗側ハードウェア追加 ¥0、中央サーバ Dell R660 × 2 で ¥240 万。10,000 店舗で約 ¥8 億円のコスト削減を実現可能。

8.4 HA (Active-Active) シーケンス

1. Node A 起動 → lease 90s TTL で central_nodes に書込
2. Node A の ShardManager が capacity 5,000 まで未割当店舗を claim
3. Node B 起動 → 同様に capacity 5,000 まで claim
4. Node A 障害 (lease 失効) → Node B が他ノードの担当を最大 90 秒以内に検出
5. Node B の ShardManager が Node A の担当店舗を引き取り (capacity 内で)
6. 復旧後、Node A が再起動 → 未割当店舗を再 claim → 自然に rebalance

8.5 Circuit Breaker

NVR 障害が広範囲化したとき、毎ポーリングで時間と帯域を浪費しないよう、店舗ごとの状態機械を持つ。

状態意味遷移条件
CLOSED通常稼働初期状態、または HALF_OPEN で 2 連続成功
OPEN障害隔離中 (即拒否)5 連続失敗
HALF_OPEN復帰試行 (1 回だけ実行可)OPEN から 60 秒 cooldown 経過
