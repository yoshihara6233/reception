1. 背景・課題

問題の本質

Jアラート発令時、店舗担当者は手動でNVR/DVRを検索して発令前後の映像を確認し、手動で報告書を作成している。BCP（事業継続計画）の証跡として「発令時刻前後の映像保全」と「自動報告書」を顧客が求めている。

現状ワークフロー（As-Is）

1
Jアラート発令（サイレン・スマートフォン通知）
2
担当者がNVRを手動操作して発令時刻近辺を検索
3
映像を目視確認して内容をメモ or スクリーンショット
4
Word や Excel で報告書を手作業で作成
5
上長・当局・保険会社へ提出
⏱ ロスタイム：発令〜報告書完成まで平均 2〜4 時間

2. 要件定義

最低要件（顧客確認済み）

#要件優先度
R1Jアラート受信を自動検知必須
R2発令前後の映像を自動保全（クラウドストレージへ）必須
R3担当者への自動メール通知（映像リンク ＋ 報告書PDF添付）必須
R4monitor app 上でBCPイベント一覧・詳細が確認できる推奨
R5手動テストトリガーで全フローが確認できる推奨

設計前提

  1. Jアラート受信はクラウド側が外部API経由で行う（気象庁XML 無料フィード）
  2. 映像はNVRに既に存在するため「保存」でなく「取得・転送」が本質
  3. 既存のVODモード（edge-agent）を録画取得の基盤として活用する
  4. i-PRO NVRはVOD未実装（Phase 8）のためMVPでスキップ、Univiewer店舗のみ対応
  5. 将来的に当局・保険会社への提出用途が生じる可能性がある

3. アプローチ選定

案概要工数採否理由
A：MVP クラウドJアラート受信→エッジ自動録画→PDF自動メール送信 M（2〜3週間） 非採用 確認画面なし。設定は固定値。顧客デモに弱い。
B：フル機能 MVP＋専用BCPレビュー画面＋手動テストトリガー＋店舗設定 L（CC: 3〜4日） 採用 担当者がmonitor app内で発令履歴・映像・報告書を一元管理。テスト可能。

bcp.ts 実装概要

処理詳細
カメラスキップi-PRO（vendor='ipro'）は upload_status='skipped_ipro' で即スキップ。FFmpeg不起動。
RTSP録画ffmpeg -rtsp_transport tcp -i <rtsp> -t <durationSec> -c copy /tmp/<clipId>.mp4
ストレージアップロードSupabase Storage バケット bcp-clips、パス {eventId}/{clipId}.mp4
/tmp クリーンアップfinally ブロックで即時削除（アップロード失敗時も必ず削除）
並列制限手製セマフォア（semaphore.ts）で同時RTSP接続数を max 4 に制限（Uniview NVR上限）
全失敗ガードsuccessCount === 0 の場合 → bcp_events.status='failed' + 失敗メール送信
並列実行Promise.allSettled() — 失敗カメラがあっても他カメラの処理を継続

toBcp() — ステートマシン追加

// claude/edge-agent/src/state-machine.ts
async toBcp(cmd: BcpCaptureCommand): Promise<void> {
  if (this.state === 'bcp') {
    logger.info({ eventId: cmd.eventId }, 'bcp: already active, skip')
    return  // 進行中BCP中は新規コマンドを無視
  }
  await this.toIdle()
  this.state = 'bcp'
  await heartbeat('bcp')
  try {
    await runBcpCapture(cmd)
  } finally {
    this.state = 'idle'
    await heartbeat('idle')
  }
}

手製セマフォア

// claude/edge-agent/src/util/semaphore.ts
export class Semaphore {
  private queue: Array<() => void> = []
  private running = 0
  constructor(private readonly limit: number) {}

  async acquire(): Promise<void> {
    if (this.running < this.limit) { this.running++; return }
    await new Promise<void>(res => this.queue.push(res))
    this.running++
  }
  release(): void {
    this.running--
    this.queue.shift()?.()
  }
  async run<T>(fn: () => Promise<T>): Promise<T> {
    await this.acquire()
    try { return await fn() }
    finally { this.release() }
  }
}

// bcp.ts での使用
const sem = new Semaphore(4)  // Uniview NVR 同時 RTSP 上限
await Promise.allSettled(clips.map(clip => sem.run(() => captureCamera(clip))))

11. エンジニアリングレビュー（D1〜D8）

D1 — PR構成 採用: 2PR構成

✅ 採用: 2PR構成（Foundation PR → Feature PR）

PR 1 (Foundation): DB migrations + Resend email for monitor + @react-pdf/renderer + Supabase Edge Functions setup

PR 2 (BCP Feature): edge-agent BCP mode + UI screens + J-Alert poller + PDF webhook + unit tests

理由: email・PDF・Edge Functionsはmonitorに存在せず、全てゼロから追加が必要。インフラ層と機能層を分離することで、PRレビューの認知負荷を下げる。

発見した隠れた前提**: 設計書で「既存インフラ流用」と記載されていたが、実際にはmonitorにemail・PDF・Edge Functionsは一切存在しなかった。

D2 — コマンド配信方式 採用: pending_command ポーリング

✅ 採用: 既存の pending_command ポーリング（2秒間隔）を流用

経緯: 設計書は「Supabase Realtime broadcast」と記載していたが、既存の realtime.ts を読んだところ、DBポーリング方式が実装済みだった。Realtimeを新規実装すると2つの並列コマンドパスが生まれ、信頼性特性が異なることが問題になる。

利点: エッジがオフライン中でもコマンドがDB上に残り、再接続後にピックアップ可能。BCP（過去映像取得）では2秒の配信遅延は無視できる。

D3 — BCP進行中の2本目Jアラート処理 採用: スキップ（進行中を中断しない）

✅ 採用: state === 'bcp' の場合、新規コマンドをスキップして継続

理由: 現在のBCP録画を中断して再起動すると、進行中のクリップが中途半端なまま残る。多発するJアラートケースでは最初の録画完了を優先する方が証跡として有用。

D4 — /tmp ファイル管理 採用: アップロード後即時削除

✅ 採用: try/finally で即時削除（アップロード失敗時も保証）

実装: finally { await fs.unlink(tmpPath).catch(() => {}) }

理由: セマフォア4枚では最大〜960 MB のピーク使用量になる。録画完了後に保持し続けるメリットはなく、ストレージ枯渇リスクを避けるため即削除が合理的。

D5 — 複数エッジデバイス対応 採用: 全デバイスに送信

✅ 採用: 店舗の全オンラインデバイスにコマンドを送信（status != 'offline'）

帰結: 複数デバイスが並列にクリップを作成するため、各デバイスが直接 bcp_events.status を更新すると競合が発生する。これを解決するため、Postgres トリガー（trg_bcp_clips_complete）でDB側が集約を担う。

D6 — 全カメラ失敗時の処理 採用: 失敗ステータス + 失敗メール

✅ 採用: successCount === 0 の場合、status='failed' + 失敗メール送信

理由: クリップが1件も存在しない状態でPDF生成を起動すると空のPDFが生成される。ユーザーに「録画に失敗した」ことを明示する方が適切。部分失敗（一部カメラのみ失敗）はclips_uploadedとして扱い、PDFに失敗カメラを記載する。

D7 — RTSP並列接続制限の実装方式 採用: 手製セマフォア

✅ 採用: edge-agent/src/util/semaphore.ts（約30行）を新規実装

理由: p-limit など外部パッケージを追加することなく、シンプルな非同期セマフォアを手書きで実装。テスト容易性が高く、依存関係を増やさない。

D8 — テスト追加 採用: vitest + 12ユニットテスト

✅ 採用: edge-agent に vitest をセットアップし、BCP機能のユニットテストを12本追加
