01この資料について / プロダクト概要

最初に読む1枚。詳細は各章と参照資料へ。

Intereco Monitor は、多店舗チェーン向けのレコーダ統合監視 SaaS（本部一元監視プラットフォーム）です。各店舗の既設レコーダ（NVR）・カメラを小型エッジ端末経由でクラウドに接続し、本部からライブ・録画・地図・死活をひとつの画面で監視します。その基盤の上に、4つの業務モジュールが載っています。

モジュールひとことで状態
Monitor コアライブ（16分割グリッド／単カメラ4方式）・録画再生（VOD／4ch同期）・店舗地図・エッジ死活・視聴監査本番稼働
BCP（Jアラート連動）地震・津波・ミサイル情報の受信時に前後スナップショットを自動保全し、証跡PDFを自動生成・メール送付本番稼働
巡回（Patrol）全カメラを定時（既定4時間毎）に自動撮影して証跡化。日次PDFレポート・手動トリアージ本番稼働
発報(Alarm)カメラ/NVRのイベント通知を受けて全記録・メール/Webhook通知・前後8コマのフォレンジックタイムライン本番稼働
手荷物検査iPadキオスク＋顔認証（AWS Rekognition）で従業員/来訪者の入退室と退室時手荷物検査を記録。2カメラ同期映像で本部確認本番稼働（2026-07-20 実機確認済）

対象市場と販売ストーリー（5カ年計画より）

家電量販店・倉庫業・衣料品・警備会社・ビル管理。2026 パイロット（3店）→ 2027（100店）→ 2028（1,000店）→ 2029（3,000店）→ 2030（10,000店）。既存の価格前提は月額 ¥3,200/店（税抜）（docs/5year_sales_plan.xlsx）。本書 §16 でこれを「基本＋オプション」に再構成した価格案を提示します。

04基本設計

4.1 デプロイと CI

  • Vercel プロジェクト intereco-monitor・本番ブランチ monitor-prod（保護・PR経由必須）。
  • CI（GitHub Actions）: paths-filter で変更アプリのみ typecheck/test/build/lint。authz ジョブ＝実DB＋RLSのテナント×ロール契約テスト。集約チェック ci-passed がマージ必須ゲート。
  • Vercel Cron: エッジ死活 2分毎 / VODクリーンアップ 03:00 / 巡回 10分毎 / 巡回日報 05:00 JST / 発報再ディスパッチ 2分毎 / 手荷物検査日次 05:00 JST。

4.2 エッジ agent（状態機械と接続）

  • 状態機械: Idle → Grid | Live | VOD（同時1モード）＋ SFU-publish / BCP capture。Idle は心拍のみ。
  • 接続: Supabase へアウトバウンドのみ。指令は Realtime broadcast＋edge_devices.pending_command ポーリング（〜2秒）。心拍 last_seen_at 60秒毎、3分無応答で監視中断扱い。
  • 登録: QRワンタイムトークンで自己登録（enroll→device_token→bootstrap で鍵/設定取得）。

4.3 自律 OTA（エッジ遠隔更新）

  • クラウド宣言型: 管理画面で端末毎に desired_agent_version（gitショートSHA）を指定 → エッジが bootstrap ポーリング（〜5分）で検知 → checkout / bun install / typecheck プリフライト → current シンボリックリンク切替 → 再起動。
  • 2層ロールバック: (1) 起動後ヘルスプローブ不合格 → known-good へ自動復帰 / (2) クラッシュループは systemd OnFailure でロールバックサービス起動。
  • 実機レイアウト: /home/intereco/edge/releases/<sha>/・秘密は shared/agent.env（systemd EnvironmentFile）が正。

4.5 i-PRO NVR（httpdl.cgi）の実測制約と設計指針 — 2026-08-01 負荷試験

PoC 実機（WJ-NU101・カメラ2台）で httpdl.cgi の常用可否を実測した（生データ: docs/ipro-loadtest-20260801.csv・詳細: docs/ipro-meeting-prep.html §4.5）。 録画切り出しを使う全機能（VOD・手荷物検査クリップ・BCP・発報前フレーム）の設計前提になる。

実測項目結果
常用負荷（2分クリップ×50回・72秒間隔）50/50 成功・ビジー0・取得時間 中央値 4.6 秒・総転送 0.88GB。試験中の録画に欠落なし → 検査 1日200回運用は余裕（NVR占有 計約33分/日）
再生 DL の同時実行上限2 本まで。3本目からは即時 X-RecData-Satus=3（ビジー・約1秒で返る）。→ エッジは downloadIproNvrMp4 を NVR(endpoint) 単位のセマフォで並列2に制限（超過は失敗でなく順番待ち・PR #241）
UID・コマンド間隔UID は 17 本同時取得可（仕様書の「同時最大16」は dlogin 数の上限ではない）。間隔ゼロ連続10回も劣化なし（「3秒間隔」は実効強制でない）
KIND=MP4 の生成方式無劣化のコンテナ詰め替え（H.265/H.264 ともコーデックそのまま・実時間の約26倍速）＝画質劣化なし・NVR側トランスコード負荷なし
窓長・秒粒度≤1時間制約は実在（61分窓は生の HTTP 500）。STARTTIME の秒≠00 指定は実質動作する（直前キーフレームから開始）が未文書のため依存しない（現行の分丸め実装を維持）
死活監視の外部取得UID 不要 CGI で HDD 容量/残量（recordedtime.cgi）・CH別カメラ接続（as_getinfo.cgi?FILE=2）・CH別録画状態（FILE=3）が取得可。SNMP は応答なし → NVR 死活監視はこの3本のポーリングで実装する

運用上の教訓（同日の実弾BCPより）: BCP・発報前コマ・検査クリップは「レコーダのタイムライン」から切り出すため、NVR の時計ズレがそのまま証跡に乗る（実例: NTP 未設定で +3分）。開通チェックリストで NVR・カメラ・エッジの NTP 統一を必須とする。

06詳細設計 — BCP（Jアラート連動）

目的: Jアラート（震度・津波・ミサイル）受信時に、前後の映像スナップショットを自動保全し、保険・監督対応の証跡PDFを自動生成する。場所: src/app/bcp・api/bcp-webhook・エッジ modes/bcp.ts

JMAフィードをポーリング
(Edge Function jalert-poller)→ 対象地域の店舗に
bcp_events 起票→ エッジが8コマ撮影
T-5〜T+30分・4並列→ PDF自動生成
(bcp-webhook)→ メール送付・完了
  • スナップ取得元: Frigate 履歴フレーム / i-PRO NVR履歴 / Uniview / フォールバック latest.jpg（Univiewは時刻指定不可＝常に最新）。
  • 状態遷移: pending → recording → clips_uploaded → report_generated → completed（DBトリガ＋スイープで前進・失敗は failed）。
  • 画面: 統合ダッシュボード（統計カード＋アラート→店舗ツリー）/ イベント詳細（カメラ別8サムネイル・ZIP・PDF再生成・手動再取得）/ Jアラート受信履歴 / テスト発行（is_test・テストのみ削除可）。
  • 設定: 店舗毎に通知先メール・スナップオフセット・震度しきい値・津波/ミサイル有効化。
  • 通知: メールのみ（PDF添付）。LINE/SMSは未実装。
  • 保存: 非公開バケット bcp-clips / bcp-reports＋署名URLプロキシ。閲覧は視聴監査ログ（bcp_view）に記録。

07詳細設計 — 巡回（Patrol）

目的: 警備員の巡回に相当する「全カメラ定時撮影」を自動化し、改ざん耐性のある証跡と日次PDFを残す。Phase A は証跡特化（撮影と記録のみ・AI比較はP2/P3計画）。場所: src/app/security

スケジューラ判定
(Vercel Cron 10分毎)→ patrol_runs 起票→
エッジへ capture 指令→ エッジ全カメラ撮影
Frigate→ONVIF→go2rtc の順で取得→ ingest（Bearer device_token）→
patrol_findings→ 日次PDF（05:00 JST）
メール送付
  • スケジュール: 店舗毎に fixed（1日最大4回の時刻指定）または interval（既定240分）。「今すぐ巡回」は都道府県グルーピングで複数店舗一括発火。
  • トリアージ: 監視者が所見を confirmed / false_positive / review に手動フラグ。
  • 保持: 巡回run/所見/スナップは31日で自動削除。PDFレポートは長期保存（証跡）。
  • 備考: pending_command は巡回/発報/BCPで1スロット共有（競合時はリトライ側が吸収）。AI列（ai_status等）はスキーマに存在するが未使用。

08詳細設計 — 発報（Alarm）

目的: カメラ/NVRの接点・通知イベント（動体・妨害等）を全記録し、通知とフォレンジックタイムラインを提供。検知はデバイス側に委譲（エッジは自前検知しない）。場所: src/app/alarms・エッジ src/alarm/

カメラ/NVRのHTTP通知→ エッジ :9080 受け口
共有トークン検証・即200応答→ スナップ撮影→
/api/alarms/ingest→ dedup（既定120秒窓）→記録
→メール/Webhook通知→ 全カメラ×8オフセット
フレーム収集（〜3分）
  • タイムライン: オフセット [-5, 0, +5, +10, +20, +30, +60, +180] 秒。マイナスは録画から抽出、0以降はライブ撮影（遅延時は録画抽出にフォールバック）。詳細画面からライブ単体 / 16分割 / 録画（±5分）/ 4ch同期VODへ遷移。
  • 確認ワークフロー: new → ack → closed（再オープン可）・reviewed_by/at 記録。
  • 通知制御: 二重送信ガード（notified_at）・店舗別 enabled・静穏時間（JST・日跨ぎ対応）。抑止時も記録は残る。
  • 耐障害: クラウド不達はエッジ側スプール（24h/200件・oldest-first）で復旧時再送。タイムライン指令競合は 2分毎cronが30分間再ディスパッチ。
  • 保持: alarm_frames は31日でプルーニング。イベント行は監査として恒久保持（スナップのみ削除）。
  • 注意: ALARM_SHARED_TOKEN 未設定だと受け口が無認証になる（起動時警告あり）。実配備では必ず設定。ONVIF PullPoint購読はアダプタ実装済みだが本経路には未接続（現行はHTTPプッシュ受け）。

09詳細設計 — 手荷物検査（Baggage）

目的: 店舗の入退室（従業員/来訪者）と退室時の手荷物検査を、iPadキオスク＋顔認証＋2カメラ映像で記録し、本部が事後確認する。場所: src/app/kiosk/baggage・src/app/baggage・src/lib/baggage・エッジ workers/clip-jobs.ts

9.1 iPad キオスク（PWA）

区分×動作フロー
従業員 入室自動顔認証 → 成功: あいさつ表示（文言変更可・TTS）／失敗: スキップボタン（自動では進めない・authSkippedで記録）
来訪者 入室個人情報同意（毎回・文言設定時のみ）→ 顔撮影（手動シャッター・照合なし・当日コレクションへ登録）→ 名刺撮影（なしでも可）→ 受付記録
両区分 途中退室/入室顔認証のみの軽量イベント（2秒で戻る）
両区分 退室顔認証＋手荷物検査: 照合 →（不一致は「検査へ進む」導線）→ 検査STEP（64px大型文言・音声・各STEP無操作タイムアウトで interrupted）→ 完了メッセージ（文言変更可）
  • ログイン: 店舗別6桁PIN（scryptハッシュ・5回失敗15分ロック・原子的失敗加算RPC）→ HMAC署名 httpOnly cookie bgk_session（12h・店舗スコープ）。QR＋PIN設定画面は /baggage/ipad。
  • PWA: 店舗別 manifest（…/manifest.webmanifest）で「ホーム画面に追加」がその店舗のキオスクを開く。アイドル画面にビルドSHA＋「更新」ボタン（デプロイ後は再読込が必要）。
  • 顔登録: 未登録従業員のみ端末上でセルフ登録可（上書き不可＝なりすまし防止・差し替えは管理画面）。登録時に同意画面。

9.2 顔認証設計（AWS Rekognition）

  • コレクション: 従業員=店舗常設 baggage-emp-<store> / 来訪者=当日限り baggage-<store>-<ymd>（日次バッチで削除）。ExternalImageId は employees.id / session id。
  • しきい値 72（80から引き下げ・実環境の角度/照明で正当な顔が落ちたため）。撮影は中央クロップ2.6倍・長辺512pxで高速化、アップロードと照合は並行実行。
  • authSkipped の意味論: true は「認証を実行できなかった」（AWS未設定/タイムアウト/カメラ不可）のみ。照合できたが該当なし（no_match）は false のまま＝未特定。
  • アンマッチ方針: 顔で本人特定できた時だけ入室セッションに紐づけ。推測紐づけはしない → unmatched_entry/exit として翌日メールで管理者へ通知。UI にも「同一人物である保証はありません」警告。

9.3 本部確認（/baggage）と映像パイプライン

  • 左一覧×右詳細のマスター・ディテール。詳細=2カメラ同期プレイヤー（倍速1/2/4/8×・シーク不可）＋顔比較3列（入室/退出/従業員マスタ or 名刺・タップ拡大）。映像を最後まで再生しないと「確認済み」ボタンが押せない。
  • クリップ切出: 退室時に inspection_clip_jobs 起票（検査窓±15秒・NVR確定待ち5分・保持期限-2日が締切）→ エッジが15秒ポーリングで取得→検証（長さ80%以上）→ baggage-clips へアップロード。失敗は指数バックオフ [1,5,30,120,360]分。
  • 日次バッチ（05:00 JST）: 前日アンマッチ確定→管理者メール / 来訪者当日コレクション削除（7日ぶん掃引）/ 保持期限超過の削除（既定60日・従業員マスタ顔は対象外）/ ジョブ掃除。

  • 手荷物検査店長（baggage_manager）: middleware で /baggage・/kiosk・/api/baggage＋認証系のみ許可。ライブ視聴には一切入れない（LIVE視聴時間を増やさない設計判断）。

16.5 価格決定に必要な残論点

  • ティアの粒度: 単純なカメラ数列 vs プラン表（保持日数・同時視聴数の差別化を含めるか）。
  • 請求サイクル・日割り・最低契約期間（現状は月次のテナント×ティア集計→CSV/PDFを請求根拠とする手動運用。Stripe等の決済統合は将来スコープ）。
  • 手荷物検査の従量設計: 運用は店長の全件確認再生が前提（S3系はエグレス費で候補外）。前提訂正（720p・1024Kbps＝約15MB/本）により、大規模店（退室200件/日）の変動費は現行Supabaseでも ≈¥5,900・R2移行後（PR #199 実装済み）は ≈¥3,000。価格 +¥13,400 での採算分岐は R2で ≈890件/日（Supabaseのままでも ≈450件/日）— 大規模店ティアは不要。従量上限は安全弁として規約に明記する。
  • エッジHWの買切り/レンタルの標準をどちらにするか（保守・故障交換の責任分界）。
  • ボリュームディスカウント（100店/1,000店の階段）と5カ年計画（¥3,200前提）との整合。
