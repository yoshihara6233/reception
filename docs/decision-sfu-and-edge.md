# 決定1：高画質配信のSFU方式

## 選択肢

| 案 | 内容 |
|---|---|
| **A. LiveKit Cloud（マネージド）** | SFWをSaaSで利用。TURN/スケール/監視込み |
| B. 自前 LiveKit（OSS）on クラウドVM | 同一API/SDKを自前運用 |
| C. 他SFU（mediasoup/Janus/Jitsi等） | フルカスタム |
| D. SFU不使用（トンネル継続 or HLS集中化） | 高画質を別方式で |

## 判断軸と評価

| 判断軸 | 重み | A. LiveKit Cloud | B. 自前LiveKit | C. 他SFU | D. 非SFU |
|---|---|---|---|---|---|
| **時期厳守**(12月ベータ/2月本番) | ★★★ | ◎ 即時 | △ TURN/構築要 | ✕ 工数大 | △ |
| **内製工数**(3〜5名/品質優先) | ★★★ | ◎ 最小 | △ 運用負荷 | ✕ | ○ |
| 遅延 | ★★ | ◎ WebRTC 0.3〜0.8s | ◎ 同等 | ◎ | ✕ HLSは5〜15s |
| NAT越え/TURN | ★★ | ◎ 込み | △ 要構築 | △ | — |
| スケール(300同時/5000店) | ★★★ | ◎ 自動 | ○ 自前分散 | ○ | △ |
| **コスト**(egress) | ★★ | △ ~$0.12/GB | ◎ ~$0.05/GB+VM | ◎ | ◎ |
| SLA/信頼性 | ★★ | ◎ SLA有 | △ 自己責任 | △ | — |
| **ロック\イン/移行性** | ★★ | ◎ **OSS同一APIで自前へ低摩擦移行** | ◎ | ✕ 別実装 | — |
| 既存資産 | ★ | ◎ repoに livekit-server-sdk/WHIP実装残存 | ◎ | ✕ | — |

## コスト・クロスオーバー分析（自前が得になる点）

| 時期 | マネージド月額 | 自前(egress+VM+運用) | 判定 |
|---|---|---|---|
| 12月 | ~$45 | VM固定費>従量 → 割高 | **マネージド優位** |
| 2月 | ~$470 | ~$200 egress+$300 VM ≒ 同等＋運用工数 | **マネージド優位**(工数考慮) |
| 6月 | ~$1,400 | ~$600 egress+VM$300〜600+運用0.3〜0.5FTE | **損益分岐〜自前優位**(運用余力あれば) |

→ **6月規模で初めて自前が純コストで上回る**。それまではマネージドが時期・工数・信頼性で優位。

## 推奨：**A で開始（合意推奨）**

**LiveKit Cloud で開始**。理由：
1. **時期厳守**（12月ベータ/2月本番）に必要な内製工数を最小化。
2. **TURN・スケール・監視がマネージド** ＝ 品質優先・少人数に最適。
3. **既存コード資産**（`livekit-server-sdk`・WHIP ingress 実装が repo に残存）を復活流用。
4. **ロックインが低い**：LiveKit Cloud と自前LiveKit OSS は**同一API/SDK**。Cloud→自前は **URL/鍵差し替えレベルの低摩擦移行**。「マネージドで始め、量が出たら自前で単価を下げる」が成立。

### 移行トリガー（マネージド→自前 LiveKit OSS）
以下が揃ったら自前移行を評価：
- 月額egressが **自前TCO（VM+egress+運用工数）を継続的に上回る**（目安：6月・~$1,400/月〜）。
- **運用余力**（TURN/オートスケール/監視を担えるSRE 0.3〜0.5FTE）がある。
- データ所在/契約要件で自己管理が必要になった場合。

### 留意点
- 日本最寄りリージョンで遅延確認。
- **オンデマンド配信**（視聴時のみpublish）でコスト抑制を設計に組込む。
- 既存の「高画質=Frigate直接(ローカル)/トンネル(リモート)」は **1店PoC限り**。100店以降の高画質は SFU に集約。

# 決定2：エッジ量産（ハード/OS/プロビジョニング）

## 2-A. ハードウェア

### 技術的制約（先に確定すべき要件）
- **Frigate 物体検知 + go2rtc 再ストリーム + 最大16カメラ + 31日ローカル録画** を1台で処理。
- → **x86 + Intel iGPU（QuickSync）** クラスが妥当（H.264デコード/エンコード支援）。ARM SBC(Raspberry Pi等)は多カメラ検知/録画で力不足になりやすい。
- 31日録画 → **SSD/HDD 容量設計**（カメラ数×ビットレート×31日）。

### 選択肢と判断軸

| 判断軸 | Beelink Mini-S継続(x86 N-series iGPU) | 産業用ファンレスx86(NUC級) | ARM SBC(Pi5等) |
|---|---|---|---|
| Frigate多カメラ処理 | ○ 実績(PoC) | ◎ 余力 | △ 限定 |
| 24/7信頼性/耐環境 | △ 民生 | ◎ ファンレス/温度耐性 | △ |
| 単価 | ○ 安(~2〜4万) | △ 高 | ◎ 最安(力不足) |
| 標準化/サポート | ○ | ◎ 法人保守 | △ |
| 入手安定性(5000台調達) | △ 民生は供給変動 | ◎ 法人供給 | ○ |
| 録画ストレージ拡張 | ○ M.2/SATA | ◎ | △ |

**推奨**：**x86 + iGPU を1SKUに標準化**。PoCはBeelink継続でOKだが、**5000台調達/24/7/保守**を見据え、**産業用ファンレスx86を本命候補**として早期に1〜2機種を実機評価（Frigate実負荷・温度・MTBF・供給）。**ARMは非推奨**（多カメラ検知/録画要件に不足）。

### 要確定の sizing 入力
- **1店あたり平均/最大カメラ数**（→CPU/GPU/ストレージ/帯域の決定打）。
- **Frigate検知の有無/範囲**（全カメラ常時検知か、録画+再ストリームのみか）。検知ありなら**Coral TPU or 強iGPU**前提。
- 録画ビットレート×31日 → **ストレージ容量**。

## 2-B. OS / プロビジョニング / OTA

### 選択肢

| 案 | 内容 | 向き |
|---|---|---|
| 1. ゴールデンイメージ(SD/SSDクローン) | OS+Frigate+edge-agent+cloudflared 一式を焼く | 高速展開 |
| 2. Ansible(SSH/網経由 push) | 既知fleetの構成管理 | 既知・到達可能な小〜中規模 |
| 3. **イメージ + 初回ブート登録(pull)** | イメージ展開→初回起動で**ワンタイム登録トークン**で per-edge設定をクラウドから取得 | **量産に最適** |
| 4. 不変OS+OTA基盤(balena/Mender, Ubuntu Core) | フリート管理・遠隔OTA | 大規模(数千) |

### 判断軸
- **現地展開速度**（非エンジニアが30分で設置）→ イメージ(1/3)有利。
- **per-edge固有設定**（EDGE_ID/トークン/カメラ/SFU鍵）→ 初回ブート登録(3)が必須。
- **遠隔OTA更新**（5000台・NAT内）→ **pull型** or フリート基盤(4)。Ansible push(2)はNAT内多数で困難。
- **遠隔保守/SSH**（障害対応）→ 既存トンネル(cloudflared)を流用可。
- 運用負荷/コスト（フリート基盤は費用と学習コスト）。

### 推奨（段階導入）
- **共通：ゴールデンイメージ + 初回ブート登録（pull型 per-edge設定）**。
  - イメージにソフト一式を内蔵 → 現地は焼いて挿すだけ。
  - 初回起動で**ワンタイム登録トークン**を入力/QR → クラウドが EDGE_ID・各種鍵・カメラ設定・トンネル/SFU資格情報を払い出し。
- **OTA/更新**：
  - **Nov〜Dec(1〜100台)**：イメージ+初回登録 + 軽量なAnsible/手動で十分。
  - **Feb〜Jun(1000〜5000台)**：**pull型セルフアップデータ**（edge-agentがバージョン確認→自己更新、カナリア配信）＋遠隔SSHはトンネル。必要に応じ **Mender/balena等のフリートOTA基盤**を評価。
- **Ansibleの位置づけ**：初期構築の自動化や検証環境には有用。**5000台のNAT内push管理には非推奨**（pull/フリート基盤へ）。

### 既存資産との整合
- 現状：Ubuntu + Docker(Frigate, unless-stopped) + bun/systemd(`intereco-edge`) + go2rtc + cloudflared(`cloudflared-intereco`)。
- → これらを**イメージ化**し、`.env`等のper-edge値を**初回登録で注入**する形に整える（鍵ローテも同経路で配布＝決定1/WBS4.1と統合）。
- 旧HANDOFFの「カナリアOTA/配布SDイメージ」TODOを本決定で具体化。

# まとめ（判断軸の要点）

| 決定 | 推奨 | 最重要の判断軸 | 見直しトリガー |
|---|---|---|---|
| SFU | **LiveKit Cloud で開始**（合意推奨） | 時期厳守×内製工数×低摩擦移行性 | 6月規模で egress > 自前TCO かつ運用余力あり → 自前OSSへ |
| エッジHW | **x86+iGPU を1SKU標準化**（産業用ファンレス本命・要実機評価） | 多カメラ検知/録画の処理能力×24/7耐性×調達 | 1店あたりカメラ数/検知要件の確定で再評価 |
| エッジ展開 | **ゴールデンイメージ+初回ブート登録(pull)**、OTAは段階導入 | 現地展開速度×per-edge設定×遠隔OTA(NAT内) | 1000台超で フリートOTA基盤(Mender/balena)導入判断 |

## 次に確定したい入力
1. SFU = LiveKit Cloud で開始、で**正式合意**してよいか。
2. **1店あたりカメラ数（平均/最大）と Frigate検知の範囲**（HW/ストレージ確定の決定打）。
3. エッジHW候補（産業用x86の機種・予算・調達ルート）を実機評価対象にするか。
4. OTA基盤を内製(pull型)で始めるか、早期にMender/balena等を採用するか。
