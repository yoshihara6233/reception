2当社サービスの概要（先方への説明用・1 分）

「Recorder Monitor」は、店舗の既設レコーダー・カメラをそのままクラウド監視化するサービス。店舗にエッジ端末を 1 台置き、店舗から外向きの接続のみで動作する（ポート開放・VPN 不要）。機能は 全店ライブ表示・録画再生・死活監視・BCP（発災前後の自動取得）・巡回点検レポート・警報連携・手荷物検査（検査時刻の録画クリップを証跡としてクラウド保全）。

i-PRO 機とはエッジ端末が LAN 内で通信する。クラウドから直接レコーダーへはアクセスしない。

3映像取得の整理 — 機能 × 取得経路の対応表

当社実装が i-PRO 機に対して使っている API の全体像。すべて LAN 内・エッジ端末からの呼び出し。認証は HTTP Digest（MD5）、ONVIF は WS-Security UsernameToken（機器時刻とのずれを補正して送信）。

機能 使用 API（i-PRO 側） 当社実装の要点
ライブ監視（グリッド/単画面・低 fps） NVR: push.cgi（COMP=H265 / H264, multipart RTP）
カメラ直: ONVIF GetSnapshotUri		 push.cgi はカメラごとに 1 本だけ開いて常時受信（毎回 START/STOP するとセッション枯渇で 204 になるため）。事前に hdrctl.cgi?SCREEN=1X。UID は NVR 1 台につき 1 つを全カメラで共有し、status.cgi を 60 秒間隔で keepalive。2026-08-06 に COMP=JPEG から H.265/H.264 へ変更（§4 の 39×37 問題）。受信した RTP を再構成し、キーフレームをエッジで JPEG にデコードして配信する。
高画質ライブ（H.264 HLS） カメラ直: ONVIF GetProfiles→GetStreamUri→RTSP RTSP URL は静的に組まず ONVIF で取得（NU 配下カメラは rtsp://<ip>/ONVIF/MediaInput?profile=… の動的形式）。go2rtc 経由で HLS 配信。H.265 はエッジで H.264 に変換。NVR 経由では提供しない — NU101 は RTSP(554) が閉じており go2rtc に載せる手段が無いため（構成上の制約。当社 UI でも該当カメラには高画質ボタンを出さない）。
録画再生（VOD）・検査クリップ切り出し NVR: dlogin.cgi → httpdl.cgi（KIND=MP4）→ logout.cgi 時刻は UTC・分単位（秒 00 固定）で指定。同一分内に収まる短い窓は START==END で空応答になるため、開始切り捨て・終了切り上げの分丸めを実装。multipart 応答の X-RecData-Satus（0=正常/1=録画なし/2=コーデック/3=ビジー）で判定し、複数パートは連結。VOD 用 UID は都度取得・都度 logout（ライブ用 UID と分離）。
過去時刻の静止画（BCP 8 枚・発報前タイムライン） NVR: httpdl.cgi（上と同じ） 対象時刻 −1 秒〜+10 秒の窓 MP4 を取得し ffmpeg で先頭フレームを JPEG 化（窓が短いと GOP が不完全で demux 不可のため広めに取る）。録画から引けない場合はライブの現フレームで代替。
現在時刻の静止画（巡回点検・発報後タイムライン・死活監視） カメラ直: ONVIF GetSnapshotUri（JPEG プロファイル優先） RTSP セッションを消費しないため、NVR がメインストリームを占有していても取得できる。ONVIF 非対応機のみ RTSP キーフレーム切り出し（ffmpeg, TCP）にフォールバック。
発報（センサー・接点入力）の受信 カメラ/NVR の 独自 HTTP アラーム通知（通知先＝エッジ端末）
補助: ONVIF PullPoint		 エッジが LAN 内で HTTP 受け口を立て、i-PRO 側のアラーム通知先に設定。通知がタイムアウトしないよう即 200 応答→非同期処理。動体検知ではなく接点/通知のみを使用。ONVIF PullPoint（CreatePullPointSubscription→PullMessages）も実装・検証済み。
録画期間・構成の確認 NVR: recordedtime.cgi（UID 不要）/ as_getinfo.cgi?FILE=2 録画期間の裏取りと接続カメラ CH の確認に使用。表示はローカル時刻（httpdl の UTC 入力と混在する点に注意して実装）。

NU101 実機で確認済みの機器側前提

  • NVR は HTTPS のみ（80 閉・自己署名証明書）、Digest realm は Network disk recorder。
  • NVR の RTSP(554) は閉・ONVIF サーバ非提供（/onvif/device_service が 404）→ 録画取得は CGI 一択。
  • 配下カメラは標準 ONVIF/RTSP で成立（カメラごとに認証情報が異なるケースあり）。コーデックはカメラ混在（H.264 / H.265）。
  • そのため当社構成は「ライブ・静止画＝カメラ直 ONVIF、録画＝NVR の httpdl.cgi」のハイブリッド。
    【2026-08-06 追記】カメラ網がレコーダ側と分離されている店舗では、ライブ・録画とも NVR 経由のみで成立するようになった（ライブ＝push.cgi COMP=H265/H264、チャンネル列挙＝as_getinfo.cgi、録画＝httpdl.cgi）。高画質ライブのみ提供できない。

A 100 店舗案件に直結（この 6 問は必ず聞く）

Q1
WJ-NU101 の CGI 実装範囲を機種別に示す正式資料はあるか

「i-PRO NVR CGI-IF(NXNU) V15R1」を参照して実装したが、NU101 実機では dlogin.cgi / httpdl.cgi / recordedtime.cgi / push.cgi / hdrctl.cgi / status.cgi 系のみ有効で、NX 系で使える getsysteminfo / snapshot.cgi / playback 等は 404 だった。NU シリーズの対応 CGI 一覧、または機種×CGI の対応表はあるか。より新しい版の資料はあるか。

Q2
httpdl.cgi の常用（クリップ切り出しの高頻度利用）は製品想定内か

手荷物検査の証跡として、1 店舗 1 日 200 回 × 2 カメラ × 100 店舗の頻度で数分単位のクリップを httpdl.cgi で切り出す運用を計画している。①NVR 側の処理負荷と録画への影響（取りこぼしは起きないか）②HDD 寿命への影響 ③推奨される並列度・呼び出し間隔 ④X-RecData-Satus=3（ビジー）になる条件、を確認したい。

実測（§4.5）: 50 回×2 分の連続取得は全成功・録画欠落なし・同時 3 本目から Satus=3。→ 聞き方は「この使い方と負荷で長期運用して問題ないか。並列 2 が仕様上の上限か」。残る未知は ②HDD 寿命への長期影響のみ。

Q3
セッション制約の正確な単位（当社運用の妥当性確認）

資料記載の「UID 同時最大 16・同一カメラ 2 本不可・ライブと再生は同一 UID 不可・コマンド間隔 3 秒目安」について、制約の単位は UID か TCP 接続かカメラか。当社はライブ＝NVR 1 台 1 UID を全カメラ共有（keepalive 60 秒）、再生＝都度別 UID で運用し安定しているが、これは想定された正しい使い方か。

実測（§4.5）: UID は 17 本同時取得できた／間隔ゼロの連続取得も問題なし／実効の壁は「再生 DL 同時 2 本」だった。→「『同時最大 16』『3 秒間隔』の実体は何か。再生同時 2 本が正式仕様か」を確認。

Q4
WJ-NU101 の製品ライフサイクル

販売終了・修理/サポート終了時期、ファームウェア（特にセキュリティ修正）の提供方針。既設 100 台を今後 5 年程度使い続ける前提で、リスクと後継機種（リプレイス時の互換性）を確認したい。

Q5
NVR 死活監視・HDD 健全性を外部から取る公式手段

当社は NVR/カメラの死活監視を標準機能として提供している。NU101 で①機器状態・エラー状態の取得 CGI ②HDD の S.M.A.R.T / 劣化状態の外部取得 ③障害発生時の能動通知（メール・HTTP 通知・SNMP trap）は何が使えるか。（現行の顧客運用では NVR 故障の検知手段がなく、ここを商品価値にしたい）

実測（§4.5）: HDD 容量/残量・CH別カメラ接続・CH別録画状態は既存 CGI で取得できることを確認済み。SNMP は応答なし。→ 残る質問は「機器エラー・HDD S.M.A.R.T・能動通知の公式手段」に絞り込み。

Q6
独自 HTTP アラーム通知の正式仕様

カメラ/NVR のアラーム通知先を当社エッジ端末に向けて発報連携している。通知のリトライ有無・タイムアウト・同報数の上限・HTTPS(TLS) 対応の正式仕様を確認したい。（当社は通知を取りこぼさないよう即 200 応答で受けている）

Q7
時刻系の確認

①httpdl.cgi の STARTTIME/ENDTIME が UTC、recordedtime.cgi の表示がローカル、という理解で正しいか ②NVR の NTP 同期の推奨設定 ③機器時刻と実時刻のオフセットを外部から取得する手段はあるか（切り出しクリップと実時刻の突合精度に効く）。

Q8

Q9
KIND=MP4 の生成方式

録画ストリームのコンテナ詰め替え（無劣化）か、トランスコードか。JPEG 録画が KIND=MP4 で取れない（Satus=2）ことの確認も。

実測（§4.5）: H.265/H.264 ともコーデックそのまま・26 倍速転送 → 無劣化詰め替えと確認済み。→「この理解で正しいか（全機種・全 FW で同じか）」の確認のみ。

Q10
ONVIF 対応方針

NU101 は ONVIF サーバ非提供（Profile-G/Replay なし）で正しいか。NX 系での Profile-G 対応機種はどれか。配下カメラの ONVIF は NVR 接続中でも外部利用してよい設計か（当社はカメラ直 ONVIF＋NVR 録画のハイブリッドで運用中）。

Q11
push.cgi の挙動

【2026-08-06 更新】COMP=JPEG は、JPEG 配信を持たないカメラに対して 39×37 のプレースホルダを HTTP 200 で返す（実機確認）。これは仕様か。「このカメラは JPEG を配信できない」を事前に判別する手段はあるか。当社は COMP=H265/H264 を受けてエッジでデコードする方式に全面移行し、この依存を解消済み。
COMP=H265/H264 の multipart は 1 パート＝RTP パケット 1 個（PT 98/101・拡張にカメラ番号と時刻）という理解で正しいか。INTERNETMODE=ON の意味。START が 204（空）を返す条件（当社はセッション枯渇と推定し永続ストリーム化で回避）。

Q12
snapshot.cgi の time パラメータ

過去時刻指定が FW v3+ のみ、旧 FW は無視して最新フレームを返す、という理解で正しいか。対応可否を機械的に判別する方法はあるか。

Q13
カメラ CGI の Accept ヘッダ 400 問題

仕様書 §1.3 に Accept ヘッダ付きで 400 になる旨と get_randomnum→&Randomnum= の回避策の記載がある。

実測（§4.5）: 手元の WV-U1132A / WV-SW158 では再現せず（Accept 付きでも 200・get_randomnum 自体なし）。→「どの機種/FW 世代で必要な対策か」を確認。

Q14
カメラ RTSP の同時接続数

過去に NVR がメインストリームを掴んでいる状態で外部から RTSP SETUP すると 503 になる事象があった。カメラのストリーム同時接続数の考え方（プロファイル別の枠、JPEG 系は別枠か）を確認したい。

実測（§4.5）: 現行 FW では NVR 録画中でも H.265 メイン 4 本同時に成功（上限未到達）。→「同時接続数の正式仕様と、503 が出る条件」を確認。
